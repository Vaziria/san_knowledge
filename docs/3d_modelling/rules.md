# 3D Modelling Rules

Rules for building 3D figures with Three.js in `typescripts/animation`. They come from building the grand piano (`src/figures/Piano.ts`) and the MIDI keyboard (`src/figures/MidiPiano.ts`). Follow them for every new figure.

## Project

1. The project is Vite + TypeScript + `three`, plus React, zustand and shadcn/ui (on Tailwind CSS) for the control panel only (see [Control panel](#control-panel)). The dev server runs on port **8087** (`npm run dev`).
2. One figure per file in `src/figures/`. The file is named exactly like its class, in PascalCase: `MidiPiano.ts` exports `class MidiPiano extends THREE.Group`. On Windows, rename a file's case in two steps (`midiPiano.ts` → a temporary name → `MidiPiano.ts`), because the file system ignores case.
3. **Every figure has a spec** in a markdown file with the same name next to it: `MidiPiano.ts` has `MidiPiano.md`. See [Figure specs](#figure-specs).
4. **A figure with distinct body parts gets its own folder**, named like the figure. Example: `src/figures/Boat/`, which holds:
   - `Boat.ts`, which puts the parts together and decides where each part's pivot sits on the figure
   - `Boat.md`, the spec
   - one file per part, named like its class in PascalCase: `Hull.ts`, `Rudder.ts`
   - `parts.ts` (lowercase, since it isn't a class) for what the parts share: the materials built from the theme, and helpers such as `mesh()` and `gridGeometry()`

   Each part is a `THREE.Group` whose origin is its pivot (the neck, shoulder, heel or tail base, the rudder's hinge). It takes the shared materials, plus `side: -1 | 1` when it comes in a left and right pair. The part owns its shape and its resting pose. The figure owns where the part is placed, and exposes each part as a `readonly` field (`boat.hull`, `boat.rudder`, an animal's `leftFrontLeg`) for animation. A family of figures that share their parts shares one folder instead (`animals/`, `Tree/`, `Grass/`, `objects/`). The penguin was this rule's example until it moved into the animals (Animals rule 16).
5. **Resting poses go in an inner group** inside the part (a wing's outward tilt, a foot's outward turn, a foot's scale), so that the part's own rotation is 0 at rest and animation only has to add movement.
6. The preview shows one figure at a time. Each figure has an entry in the `previews` table in `src/previews.ts` (the figure, camera position and target, and its demo animation), and the tree on the panel's Figures tab or `?figure=<name>` picks one. The default, `defaultFigure`, is the figure being worked on. Figures are never deleted when they stop being the default. A demo that plays several behaviours in turn is a list of steps, each a start action and a done test (a time, or a state such as "back at the start" or "stopped"), because some behaviours last as long as the figure makes them.

   **One part at a time,** as the user asked ("figure can be preview by part", task 16): a figure's parts (rule 4) are listed in `src/parts.ts`, in the order the Figures tree shows them under the figure, and `?part=<name>` (`head`, `left-front-leg`) shows one on its own.
   - **The list is type-checked** against the figure's own fields: a field that holds an Object3D (or a list of them) is an error until it is listed, as a part (`true`; or, for a list, the names of its equal runs in order, like the frog's leg segments, left leg first) or as none (`false`, the speech bubble). So a new figure with parts, or a new part, gets its line there. A figure with no parts, or only one (the cloud's body), has none.
   - **What shows:** `partPreview()` builds the figure's own preview, poses it as its first frame (`update(0, 0)`), and takes everything but the part off every camera layer (`layers.disableAll()`). `visible = false` would not do: it hides what is inside too, and a part can hang from a mesh that is hidden. The parts inside the part go as well (the bird's body holds its head, wings, tail and legs); lights stay. It keeps its place on the figure, in the environment shown, and stands still: no demo and no behaviours, which are the whole figure's.
   - **Its view:** the camera looks at the part from the way the figure's preview looks at the figure, from 2.7 times the radius of the ball round the part, aimed a little right of its middle so it sits clear of the panel. The sun's shadow fits the part (`Preview.bounds`). The same function comes back for the same part, so the stage sees it unchanged and a new environment keeps the view.
7. Everything is built in code from primitives. No imported model files (`.glb`, `.obj`).
8. **Where the project stands is written in `docs/states/`** (`typescripts/animation/docs/states/`), as the user asked ("every development state summary in typescripts/animation is recorded in typescripts/animation/docs/states/*.md"). It is the "Writing Summary Development State Report" step of the [development lifecycle](../development_lifecycle.md), which files state reports by context; here the folder is flat, one file per area of the project.
   - **The files:** one per area, in lowercase with underscores (`lake_meeting.md`, `environments.md`, `control_panel.md`, …), and [`index.md`](../../typescripts/animation/docs/states/index.md), which lists every area with its one-line state and the date it last changed. A new area gets a file and a line in the index.
   - **Each file** starts with `# <Area> state` and a line with the date and the work that last changed it, then: What works (linking the specs, the rules and the source files, since links become `reference` edges in the knowledge graph), How it was last checked (with dates), Known issues and left for the user, Open questions, and History (one dated line per change, newest first, pointing to the task file).
   - **Rewritten, not appended to,** apart from History: a state that is no longer true is removed. Write what the code does, not what a task or a spec hoped for; where they differ, the file says so.
   - **When:** whoever finishes a piece of work here, a task or work the user gives directly, updates the files of the areas it changed, and the index, before calling it done. A task's Done section says what the task changed; the state file says where the area stands now. Work that changes no behaviour (a comment, a rename) needs none.

## Control panel

The preview has a control panel in the top right, and it will grow a lot. It has vertical tabs on its right edge, by the screen's edge, as the user asked:
- **Figures**: a searchable tree of the figures by folder
- **Terrains**: a searchable tree of the terrains, like the Figures tab; picking one shows it on its own (see [Terrains](#terrains) rule 9)
- **Behaviours**: the shown figure's behaviours
- **Story**: the stories, and the lake meeting's YouTube chat (see [Stories](#stories))
- **Environments**
- **Camera**: which way the camera looks at the figure, and walking it round the scene
- **Audio**: the sound, here and in the stream
- **Settings**: the Kuwahara filter. It had a Theme menu until felt became the only theme (see [Colour and theme](#colour-and-theme))
- **Stream**: live streaming the scene to YouTube over RTMP, drawn on the page or by the dev server

The panel is React; the scene is plain Three.js.

1. **Settings flow one way.** `src/settings.ts` holds every setting in one store (zustand). The React components in `src/panel/` read settings with `useSettings` and change them only through the setters in `settings.ts`. `apply()` in `src/main.tsx` passes every change to `src/Stage.ts`, which owns the renderer, camera, lights, effects and animation loop and shows the figure in its environment. React never touches the scene and never runs per frame. Two ways back: dragging the view away from the picked camera direction sets that setting to free (the stage's `onDirectionLost`, wired in `main.tsx`; see rule 9), and a story claiming the camera back sets it to the figure's own (`onDirectionTaken`; see [Stories](#stories) rule 10).
2. **Stage setters do nothing when the value is unchanged** (`show(preview, environment, theme)`, `setCameraDirection(direction)`, `setKuwahara(radius)`), so `apply()` can hand over all the settings on every change.
3. **Every setting is kept in the URL** under its own name (`?story=`, `?terrain=`, `?figure=`, `?part=`, `?environment=`, `?kuwahara=`, `?camera=`), so a reload keeps it. Only settings that change are written, so a figure you never picked keeps following `defaultFigure`, and until you pick an environment each figure shows in its own.
4. **A new figure or environment rebuilds the figure and its environment**, and restarts the demo. Both build their materials from the theme, and a preview is built for its environment. A new figure also moves the camera to its preview's view; a new environment keeps the view. The old geometries and materials are freed, including the `props` a demo uses outside the figure (the keyboard the penguin only holds now and then).
5. **To add a control:** add the setting to `Settings` in `settings.ts`, with its default, how it is read from the URL (`fromUrl`) and written back (`toParam`), and a setter. Give `Stage` a setter that does nothing when the value is unchanged, and call it in `apply()`. Then add the control to the tab it belongs to in `src/panel/Panel.tsx`, built from the blocks in `controls.tsx` (`Toggle`, `Slider`, `Select`, `RadioList`; see [rule 8](#control-panel)). A kind of setting that fits no tab gets a new entry in `TABS`.
6. **Check controls in a real browser session**, not only a screenshot. Drive headless Edge through its remote-debugging protocol from a small Node script: load the page, click, move the slider with the arrow keys, pick menu options, then read back the controls and the URL, and fail on any console exception. After each page load, wait for the panel to appear instead of sleeping a fixed time: with software rendering and a large Kuwahara radius it took up to 8 s. The controls are Base UI, not native inputs: the switch is `[role=switch]` with `aria-checked`, and the slider's thumb holds an `input[type=range]` that takes the arrow keys. A menu opens on a press of its trigger (`[data-slot=select-trigger]`). Pick options only inside the open popup (`[data-slot=select-content][data-open] [role=option]`): a menu that has been opened keeps its hidden popup in the page, and the penguin's Hold menu also lists `midi-piano`. The popup puts the picked option over the trigger, so in a long list (the figures) other options can be scrolled out of view or sit under the scroll arrows; scroll the option to the middle before clicking it. Read a menu's value from `[data-slot=select-value]`, because the trigger's text also holds a hidden ▼ from its icon. Open a tab by clicking its `[role=tab]`. Find the shown panel with `checkVisibility()`, not `:not([hidden])`: Base UI un-hides a closing panel only after its exit animation, and the panel hides it at once with `inert:hidden`. The figure tree's rows are `[role=treeitem]`, with the name in `.truncate`, `aria-expanded` on folders and on figures with parts, and `aria-selected` on the picked figure or part; a figure's arrow, which opens its parts, is the first `svg` in its row; the search box is `input[aria-label="Search figures"]`. Story and environments are `<label>` rows in `[role=radiogroup][aria-label=Story]` (or `Environment`), each holding a `[role=radio]` with `aria-checked`.
7. **Behaviour buttons.** The panel's Behaviours tab offers the shown figure's behaviours, named exactly as its spec writes them, one button each beside an input for each argument (a menu when the preview lists `options`, such as the fish's directions; otherwise a text field, where Enter runs it). Each preview lists them in `behaviours` in `src/previews.ts` with its arguments' defaults, and the stage hands them to the store in `src/behaviours.ts` when it shows the preview. They are actions, not settings, so they are not kept in the URL, and they are the one place the panel reaches the scene: a click runs the behaviour on the figure. The first one run stops the demo (wrap each runner with `demoStopper`), so the figure does only what it is told; the penguin also stops walking and puts down what it holds. **Restart demo** builds the preview again (`stage.restart()`, keeping the view). A value the figure can't read (an unknown chord) shows its error under the row. **When a spec gains a behaviour, add it to its preview's list.** For a figure whose spec has none (the boat, the rod, the trees), the tab says so.
8. **The panel is built with shadcn/ui**: Base UI underneath (`@base-ui/react`, preset `base-nova`), styled with Tailwind CSS v4 (`@tailwindcss/vite`). The components are copied into `src/panel/ui/`, because `components.json` points shadcn's aliases into `src/panel/`. To add one, run `npx shadcn@latest add <name>` in `typescripts/animation`. Style components with `className` in the blocks rather than by editing `ui/`, so that `add <name> --diff` shows only upstream changes. `src/panel/panel.css` holds Tailwind and the theme's colour variables; everything else is Tailwind classes. `@/` means `src/` (tsconfig `paths`, which Vite reads through `resolve.tsconfigPaths`). The blocks in `controls.tsx` wrap the components:
   - `Toggle`: a switch; clicking its label flips it too
   - `Slider`: a slider with its value in the third column. The shadcn slider draws one thumb per value, so its value goes in as a one-element list.
   - `Select`: a menu, labelled with Base UI's own `Select.Label`
   - `Action`: a button
   - `Field`: a text field
   - `Choice`: a menu with no label of its own
   - `RadioList`: a few options, one row each; clicking a row picks it, and an option's `hint` shows after it, such as the Environments tab's "figure's own"
   - `SearchTree` (in its own file): a document tree with a search box. The search keeps the leaves whose folders and name hold every word typed ("oak tree" finds `oak-tree`), and Enter in the box picks the first match. A leaf can hold leaves of its own (a figure's parts): clicking it picks it, and its arrow opens it. Its own leaves also need a word in their own name, so "bear" finds the bear, and "bear head" or "head" its head; a leaf shown only because its own leaves match is not a match for Enter. In the tree, the arrow keys move and open or close folders and such leaves, Enter picks, and typing goes on in the search box.

   The Figures tab's tree comes from `figureTree.ts`. It places each figure by the path of its spec: `animals/Bear.md` goes under Animals, and a folder named like its figure (`Boat/Boat.md`, a folder of parts) sits beside the other figures rather than being a folder. So a figure goes in its folder once it has its spec, and until then it shows at the top. A figure named otherwise than its spec names it in `SPECS` (`figureTree.ts`): the fish's three kinds share `Fish/Fish.md`, and since that folder isn't named like any of them it stays a folder, the Fish folder, as `Tree/` does (the table names the folder too, since `/Fish.md` alone also matches `animals/Fish.md`, where the fish's shapes are). The penguin's spec is `animals/Penguin.md` now, so it shows under Animals, first. Folders come first, then figures in the `previews` table's order. A figure with parts (`src/parts.ts`, [Project](#project) rule 6) opens to list them: its row still picks the whole figure, and its arrow, or → and ←, open and close its parts. Picking a part writes `?part=`; picking a figure drops it, and the Behaviours tab says a part's behaviours are the whole figure's. The tree takes the panel's height and scrolls under the search box, which stays in view.

   The Settings tab and the behaviours share three columns (label, control, value) through `grid-cols-subgrid`. The panel is a fixed 24 rem wide rather than sized by its content: a menu is as wide as the option it shows, so the panel would jump with every pick. The card is opaque, because over a dark scene a see-through card turned grey and hid the controls' light borders.

   The tabs stay mounted while hidden, so typed values and a search survive a switch. The open tab is kept in `localStorage`, so it survives the reloads a code change brings; it isn't a setting of the scene, so it is not in the URL.

   **The panel folds** down to its rail of tabs, as the user asked ("make tab can collapsible"), to see the whole scene: clicking the open tab again folds it or opens it, and so does Collapse (Expand) under the rail; any other tab opens it on that tab. Folded, the card is as wide as the rail, and the tabs' panels are hidden with a class (`group-data-[folded=true]/panel:hidden`), not unmounted, so what was typed or searched is still there. Whether it is folded is kept in `localStorage` like the open tab. A test that clicks tabs must click only a tab that isn't open, or it folds the panel. **Menus drop below their trigger** (`alignItemWithTrigger={false}` in `controls.tsx`): laid over it with the picked option on the trigger, Base UI's default, the options above the picked one went under a scroll arrow at the top of the screen, where the panel is. `ui/tabs.tsx` is the one generated file edited: it now passes `orientation` on to Base UI. The generated file dropped it, so vertical tabs had horizontal arrow keys and `aria-orientation`.
9. **The camera's direction** (the user's "CameraDirection control": the Camera tab's View menu, `?camera=`, `src/camera.ts`) says which way the camera looks at the figure. The menu also has `walk` (rule 11).
   - **The choices:** the figure's own view (its preview's camera, the default), eight directions round it named from the figure's side (it faces +z and its left is -x, so `left` shows its left flank), and `top`, straight down with its front toward the bottom of the screen.
   - **Where it puts the camera:** a direction keeps the preview's target and distance and, round the sides, the height the preview looks from (kept between 7° and 60° above level), so a figure is framed as its preview frames it.
   - **Moving there:** picking one glides the camera round the target, the short way, over about half a second (`Stage.glide`, exponential easing like every setter). The orbit controls' damping is off during the glide, so the tail of a drag can't fight it. Taking hold of the view stops a glide.
   - **Free after a drag:** once a drag turns or tips the view more than half a degree from the picked direction, the stage reports it and the menu says `free (dragged)`, so picking the same direction again moves the camera back; zooming and panning keep the direction. `free` leaves no URL parameter, since a dragged view can't be written down.
   - **A new figure** shows from the picked direction (the stage gets the direction before `show()`, so it appears from it at once, without a glide); from `free` it goes to the figure's own view, and the menu says so. A new environment keeps the view, as before.
   - **Checked** in a browser session through the remote-debugging protocol: picking directions, dragging, picking again, loading `?camera=right`, changing the figure from a direction and from free, and a bad `?camera=`, reading the menu and the URL each time and comparing screenshots.
10. **The Stream tab** streams the scene live to YouTube, as the user asked ("connect youtube streamurl with rtmp"). YouTube Studio shows the stream URL (`rtmp://a.rtmp.youtube.com/live2`, filled in) and the stream key to paste; the tab also takes a quality, 720p or 1080p at 30 fps, and has Go live and Stop. Above them are **Render** and **GPU**, as the user asked ("option to render only web + stream, or stream only, or web only"; "any configuration can use gpu or not?").
    - **How:** browsers can't speak RTMP, so a page records the stage's canvas (`canvas.captureStream`, then `MediaRecorder`, WebM with H.264 where the browser can, otherwise VP8) and posts the recording to the dev server in quarter-second pieces, one after another so they arrive in order (`src/stream.ts`); it names the recording first (`/recording`), and each piece carries its id. `stream-bridge.ts`, a Vite plugin like the OSC bridge, gives each recording a decoder (an ffmpeg of its own), which fits the picture to 1280×720 or 1920×1080 (bars where the drawing's shape differs) at a steady 30 fps and hands it back raw, in the encoder's pixels. The bridge holds 0.4 s of pictures (`BUFFER`) and sends them on by its own clock, 30 a second, to the encoder: one ffmpeg for the whole stream, which makes H.264 (3 or 6 Mbit/s) with a keyframe every 2 s, adds the Audio tab's sound as stereo AAC (rule 12; silence by default, since YouTube wants a sound track), and pushes FLV to the URL and key. It connects with the first pictures and stays connected until Stop. When no new picture comes, the last one goes again, so YouTube never sees the connection drop; a picture that comes after its turn has gone to the last one is skipped, so the stream stays 0.4 s behind and a hitch in the drawing shows no longer than it was. It is plain HTTP (`/__stream/…`), so it works through ngrok or a VS Code tunnel too. Only the scene is streamed, not the panel, and only under `npm run dev`. ffmpeg must be installed (it is, through winget) or `FFMPEG_PATH` set.
    - **Render** says where the scene is drawn. It is kept in `localStorage` and locked while live.
        - **web + stream** (the default): on the page, and the page's drawing is what streams, exactly as seen (a dragged view, a pressed piano key). A hidden tab stops drawing, so the stream freezes on its last frame: keep the tab shown.
        - **stream only**: not on the page (the stage stops its loop and hides the canvas; figures are still built, for the behaviour buttons). The bridge starts a hidden (headless) Chrome or Edge with a temporary profile of its own, which opens the page as the stream's renderer: `?renderer=1280x720` and the panel's settings (`src/streamRenderer.ts`), with no panel, drawn at exactly the stream's size (no bars), recording itself. The panel steers it: each settings change, behaviour run and Restart demo goes to `/follow`, which the bridge passes on as the Vite event `stream:follow`. It streams until Stop, whether or not the panel's page stays open; a page opened meanwhile finds it, switches to stream only and takes on its settings. In place of the scene the page shows a picture of the stream, which the hidden browser sends every second (`/preview`). A code change reloads the hidden page like any other; its new recording gets a new decoder, and the stream goes on. Errors in the hidden page go to the terminal (`/log`). The hidden browser is Chrome, Edge or Chromium where they install, or `STREAM_BROWSER`; `STREAM_BROWSER_ARGS` adds flags.
        - **web only**: on the page, and nothing streams: the stream fields and Go live are off.
    - **GPU** (on by default, kept in `localStorage`): ffmpeg encodes on the graphics card with the first of its encoders that works on this machine, each tried once on a second of test picture (NVENC, Quick Sync, AMF, VideoToolbox, Media Foundation, Vulkan, VA-API: those this ffmpeg has); the terminal says why the others don't. With stream only, the hidden browser draws on the graphics card too. Off: x264 on the CPU, and SwiftShader for the drawing (`--disable-gpu --use-angle=swiftshader`). A page's own drawing (web + stream) is its browser's choice. On this machine (RTX 3050, driver 572.83) ffmpeg 9's NVENC needs driver 610 or newer, so Media Foundation's NVIDIA encoder is used; a hardware encoder takes about a quarter of x264's CPU time at 1080p. Without the graphics card the fox scene draws at about 12 pictures a second instead of 30.
    - **An action, not a setting,** like the behaviours: nothing of it is in the URL. The stream URL, the key, the quality, Render and GPU are remembered, in `localStorage`: the key and the quality as the user asked ("when youtube stream key pasted, its cached", "cached quality option too"), from the moment they are pasted or picked; an emptied key field forgets the key. The key stays a secret on screen and in the terminal: a password field, and the bridge masks it (`••••`) in the terminal and in every message. The bridge takes only `rtmp://` or `rtmps://` URLs, because ffmpeg writes to a file when given a path; the key must be letters, digits, `-` and `_`.
    - **Status:** the page asks the bridge once a second: connecting, then live with the time, the new pictures a second (the decoder's frames less those it made twice to keep 30, from its `-progress`) and the bitrate, and a line saying what draws the pictures (the recording page's WebGL renderer) and what encodes them; while the picture stands still (2 s and more), how long and why (the page loading or hidden, or its code broken), with the terminal told at 5 s and again when pictures come back; or what ffmpeg said when it gave up (YouTube refusing the key, the network down), which also stops the recording. ffmpeg runs with `-loglevel error`, because a live recording's timestamps make routine warnings that would flood the terminal.
    - **Through code changes** (the user's "do it 1, 2" after measuring that a save cut the stream for 3 s and a broken save ended it):
        - **A save in `src/`** reloads the pages. The hidden page's new recording gets a new decoder and the stream shows its last picture meanwhile; the page that streams with web + stream records again as it loads: the start's answer names the stream's session, which the page keeps in `sessionStorage` (a reload keeps it, another tab doesn't have it) and names again with its new recording. Another page naming no session, or another, is refused (409). A page that sends nothing for 60 s (a closed tab) ends the stream; there is no stop on `pagehide` any more.
        - **A save with an error** leaves the hidden page unable to draw: the stream shows its last picture for as long as the hidden browser runs, and a save that fixes it brings the pictures back. Only the hidden browser closing, or no first picture within 15 s of Go live (40 s for the hidden browser, which has to start first), ends a stream.
        - **A dev server restart** (a save of `vite.config.ts` or a file it imports: the bridges, `meeting.ts`, `src/story/lake_meeting/events.ts`): Vite 8 makes the new plugins before it closes the old ones, and tells a plugin's `closeServer` hook whether it is a `restart` or a `close`. On a restart a running stream is carried over: it keeps the code it started with, and the new bridge passes `/__stream` on to it until it ends (a `globalThis` slot, since the new plugin comes from a new import of the file); the next stream takes the new code. The pages reload when the server is back, as after any restart. On a close the stream ends as before. On Windows the hidden browser also closes when the dev server's process ends, however it ends: Node keeps its children in a job that closes with it.
        - **Measured** on a copy of the project (its own port) streaming the lake meeting with stream only to a local RTMP listener, with the chat being read and two test viewers in the meeting: one connection from Go live to Stop through a normal save, a save with a syntax error kept for 45 s (the picture stood 48 s, then new pictures after the fix), a save of `meeting.ts` and one of `stream-bridge.ts`; the same `san_youtube` process, the viewers still there and a new one joining after the restarts. Before, the normal save cost 2.9 s without a picture and a reconnect, the broken save ended the stream after 40 s, and the restart ended it at once. A moving test picture streamed as a web + stream page by a script: no still stretch in steady streaming, a 3 s reload seen as 2.2–2.6 s of one picture, a page holding its pieces back 0.8 s seen as 0.2–0.3 s. In headless Edge, the panel's own page (web + stream): typed URL and key and 1080p kept, live, reloaded (the same session, new pictures within a second, one connection, the key and 1080p still filled in), a second tab not taking the stream, and Stop forgetting the session. The lake scene's own hitches in the first seconds after the page loads (building the scene) show as short still stretches either way.
    - **Checked without YouTube:** ffmpeg can be the RTMP server too (`ffmpeg -listen 1 -f flv -i rtmp://127.0.0.1:19350/live2/<key> -c copy received.flv`), started again after each connection so that a reconnect is caught. The test ran its own dev server (port 8123) with `STREAM_BROWSER_ARGS=--remote-debugging-port=…`, and drove headless Edge through the remote-debugging protocol: each Render mode; stream only with the GPU on and off; that the hidden page draws at 1280×720 with the panel's settings, follows a theme and a behaviour (seen in its websocket frames), records again after a reload, streams on while the panel's page is closed, is found again by a new page, and closes at Stop; the drawing-and-encoding line; and what the listener received (H.264 1280×720 at 30 fps, with AAC). Type into the fields with `Input.insertText` after clicking them; setting `value` directly doesn't reach React. A menu's shown value is in its `[data-slot=select-value]`.
11. **Walking the camera** (the user's "ability walk camera": the View menu's `walk`, the Camera tab's pad, `src/walk.ts`) walks it round the scene in the first person, as a person would.
    - **Where:** `walk` starts from where the camera is, looking at what it looked at, and glides down to eye height (1.6 m, `?eyeHeight=`) over the ground below it, or over the still water on the lake. The environment says how high to stand and how far the ground reaches (`Environment.ground`: the lake's `groundAt()`, raised to the water level; the floor and the grass flat; the reach measured from the ground's meshes, a meter short of their nearest edge), so the camera rides the lake's humps and stops before the land ends. It walks through trees, rocks and figures: there is no collision.
    - **How:** a pad of eight buttons that walk while held (forward, back, step left and right, turn left and right, look up and down), each lit while its move is held, by a key too; and keys while no field, menu, slider, tab or tree has the focus: W S or ↑ ↓, A D, Q E or ← →, R F, and Shift to run (2.5 times as fast). Speed (1.4 m/s, `?walkSpeed=`) and eye height are sliders. A drag turns the view the way dragging a photo sphere does (the ground under the pointer stays under it), and the wheel steps half a meter. The orbit controls rest while it walks.
    - **Held moves** are in one store (`walk.ts`), each with who holds it (a key, a pointer, a focused button), so letting go of one of two doesn't stop the move; a lost focus or a hidden page lets everything go, so nothing walks on by itself. The stage turns and moves the walker by what is held, at speeds per second, and the camera follows it closely (exponential easing), which smooths the ground's bumps and the glide down.
    - **Leaving:** picking another view ends the walk, and the camera glides there from where it walked to. The walk ends before the new view is recorded, since the orbit controls taking over would otherwise be read as a drag away from it, and the menu would say `free`. A new figure or environment doesn't move a walking camera.
    - **Stream only:** the held moves go to the dev server's hidden browser too (`/follow` with `walk`), which walks its own camera; the speed and eye height go with the other settings.
    - **Checked** in a browser session through the remote-debugging protocol. The test reads the camera by wrapping three.js's `Camera.updateMatrixWorld` from outside (three.js makes each renderer's `render()` in its constructor, so the prototype has none to wrap) and compares it with the lake's `groundHeight()`: eyes over the ground and over the water, 2.8 m in 2 s of W along the view, 90° in 1 s of E, the pad (lit while held), the wheel, a 100 px drag turning 100 px of view, a key typed into a field not walking, the URL's speed and height, stopping a meter short of the land's end, another view ending the walk, a new figure keeping it, and the hidden browser walking in stream only.
12. **The Audio tab** (the user's "tab audio source" and "option loop"; `src/audio.ts`, `src/panel/AudioTab.tsx`, `audio-bridge.ts`) picks the sound: none (the default), one file, every file in turn, or an input device. Loop plays the file, or the list, again from its start; the volume goes from 0 to 100 %.
    - **Files** are the dev server's: `typescripts/animation/audio` (git-ignored: music is big, and not ours to publish), or `AUDIO_DIR`. Add files puts files there from the panel, so it works through a tunnel too (`POST /__audio/files?name=`: a plain audio file's name only, never over one there, written beside it first so a cut-off upload never looks like a file). `GET /__audio/files/<name>` serves one with ranges, for seeking. A picked file that isn't there any more gives way to the first that is.
    - **Devices** are the dev server machine's inputs as ffmpeg opens them: DirectShow on Windows (here only "Microphone (WO Mic Device)"), AVFoundation on macOS, PulseAudio sources on Linux (their monitors record what plays). For Sonic Pi, or anything playing on that machine, the machine needs a device that records its output: Stereo Mix where the sound card has one, or a virtual cable such as VB-CABLE with Sonic Pi playing into it.
    - **In the stream** the dev server makes the sound, so it is the same with either Render, and it changes while live without the stream stopping (`POST /__stream/audio`; the start sends it too, and a source it can't play leaves silence and says why). `AudioFeed` writes 44.1 kHz stereo 16-bit PCM into ffmpeg's fourth pipe (`-f s16le -i pipe:3`) by its own clock, from a second ffmpeg that decodes the source (a file up to a second ahead, waiting while that is full; a device as it comes, at most 0.3 s kept), and silence wherever the source has nothing. Only whole samples are taken from the decoder: half of one puts every sample after it out of step, which sounds like noise. A file that ends starts again, or the next plays, and the second decoded ahead covers the start, so a loop has no gap. The sound starts with the first picture ffmpeg gets, and waits for ffmpeg, all of it (up to 20 s), until ffmpeg reads it: ffmpeg looks into the pictures' first seconds before it reads the sound, and sound dropped meanwhile put it behind the pictures. `-shortest` is gone: with a live sound it held the pictures back for 10 s at the start (its buffer), and Stop ends both pipes instead, so ffmpeg finishes at once. The raw sound input is not probed (`-probesize 32 -analyzeduration 0`).
    - **Here:** with Play here (on by default) the page plays the file, or the list, in an `<audio>` element, looping as the stream does; a device's sound stays on the dev server's machine. After a reload the browser plays sound only after a click on the page, so the tab says so and the next click starts it. The choice is kept in `localStorage`; a page opened while a stream runs takes on the stream's.
    - **Checked** end to end with a test dev server (its own `AUDIO_DIR`) and a local RTMP listener, measuring the received sound with ffmpeg's `volumedetect`: two 4 s tones added through the panel (by `DOM.setFileInputFiles`), the first picked and playing here; a path and a taken name refused, a range answered 206; web + stream with the tone looping at 50 % (6 dB under the file, and no dip across the loop points), then silence picked live (-91 dB to the end); stream only with every file and no loop (tone a, tone b, then silence, in the status and in the sound), then the WO Mic device picked live; folding by the open tab, kept after a reload, opened by another tab, and by Collapse and Expand. A stream-only stream with silence was checked on its own too: live in 3 s at 30 fps, and stopped at once.

## Figure specs

1. The spec (`<Figure>.md`, next to `<Figure>.ts`) belongs to the user. It says what the figure is and how it behaves. The code follows the spec, not the other way round.
2. Before changing a figure, read its spec. When the spec changes, bring the code in line with it.
3. Don't rewrite or reformat the user's spec text. If a spec is missing, write a short draft from the existing code, say at its top that it is a draft for the user to correct, and use the same layout as the other specs.
4. Implement API names exactly as the spec writes them, even when they break the usual TypeScript style. `MidiPiano.md` asks for `PlayChord(chord string)`, so the method is `PlayChord`, not `playChord`. Point to the spec in a comment next to such a method.
5. Where the spec is silent, choose a sensible behaviour, write it in the code comment, and tell the user so they can put it in the spec. For example, `PlayChord("A")` presses A major with the root in the C4 octave and releases the previous chord.
6. Layout of a spec, as the user wrote it:

   ```markdown
   # <Name> Figure.

   ## Animation Behavior.
   1. `MethodName(arg type)`

       Example:
       `figure.MethodName("value")`
   ```

## Reference images

1. When the user gives a reference image, match its **shape and proportions** part by part: list the differences first (head size, face, beak, body shape, wings, material), then fix them, then compare a screenshot with the reference again.
2. Match its **colours through the theme**, never by hardcoding them in the figure: map the reference's colours onto felt's roles. The penguin reference is where `felt` came from (black, off-white, orange, matte fabric), and felt is now the only theme (`defaultTheme` in `theme.ts`; see [Colour and theme](#colour-and-theme)).
3. For a soft material (felt, plush), use the theme `finish` with `roughness 1`, no clearcoat, and a low `sheen` (about 0.3). A strong sheen turns black into grey and orange into salmon.
4. Parts that are shiny on any material, such as eyes, use `gloss(color)` from `theme.ts` rather than the theme's finish.
5. To shape organic parts, `blob()` in `animals/parts.ts` takes a `taper` (`{ top, bottom }`) that narrows one end: a pear-shaped body, a wing narrowing to its tip (the old penguin's `ellipsoid()` did the same, before it became the user's low poly model).

## Effects

1. Post-processing effects live in `src/effects/`, one file per effect (lowercase, since they export a shader factory rather than a class), and run through three's `EffectComposer` in `src/Stage.ts`: `RenderPass` → the effect as a `ShaderPass` → `OutputPass`. `OutputPass` does the sRGB conversion that the renderer would otherwise do, so colours stay the same as without effects.
2. Render into a multisampled target (`samples: 4`, `HalfFloatType`), because a composer's targets have no antialiasing by default.
3. **Kuwahara** (`effects/kuwahara.ts`) gives a painterly look: flat patches of colour with sharp edges. It is on by default at a 5 px radius. The control panel's Settings tab has a **Kuwahara on/off switch** and a **Radius slider** (1–12 px, greyed out while the filter is off). Both keep `?kuwahara=<radius>` in the URL in step (`0` = off), so a reload keeps the setting. The radius is a shader uniform, so the slider changes it live without recompiling. It is set in CSS pixels and multiplied by the pixel ratio, capped at 24 device pixels.
4. The Kuwahara switch and slider are panel controls like any other. See [Control panel](#control-panel) for how they are built and checked.
5. Keep the Kuwahara radius around 4–6 px. At 10 px the classic four-quadrant filter shows blocky square smears and smudges small details like eyes into patches.
6. Measure colours with the effect on and off. Measured on the penguin in the getresolved brand's theme (since dropped) at a 5 px radius: background and belly unchanged, indigo within a few units (head `#4B43D7` → `#4C44D9`), slightly lighter on curved sides where it averages in the highlight (`#4740C9` → `#5049D5`).
7. **The overlay layer** (`src/overlay.ts`, layer 1) is drawn after the effects, on top of everything, so the Kuwahara filter never smears text: speech bubbles live there. With the filter on, an `OverlayPass` sits between the Kuwahara pass and `OutputPass`; with it off, `drawOverlay()` follows `renderer.render()`. The main camera and the raycaster see only layer 0. `drawOverlay()` takes the scene's background away while it draws: in three r186 a colour background clears the picture on every render, even with `autoClear` off, which first left only the bubble on an empty background.
8. **Keep thin details sharp.** The filter averages away anything narrower than its radius: at 5 px an 8 mm line 2.5 m away (about 2 px) all but vanished. `keepSharp(material)` in `effects/kuwahara.ts` marks a material to pass through the filter unchanged while everything around it stays painterly. The material stays opaque but is drawn without blending, so it writes its opacity (0.5) as the pixel's alpha, and the filter passes any pixel with alpha under 0.9 (its anti-aliased edges too). It is still drawn in the scene with depth, so it hides behind nearer things, unlike the overlay layer. The canvas has no alpha, so nothing else sees the mark. Use it only for details that must read (the fishing line), not to make whole figures sharp.

## Units, axes and origin

1. Units are **meters**, and figures are **real-world size** (a grand piano is 1.5 m wide, a white key is 23.5 mm).
2. `y` is up and the floor is `y = 0`. The front of the figure (where a person stands) faces **+z**. Width runs along **x**, left is −x.
3. The origin is the **bottom center**, on the floor. If the figure has feet, the origin is under the feet. **A handheld figure** that never stands on its own (the fishing rod) has its origin where the hand holds it instead (the pole's axis 30 cm from its butt): that is the pivot it swings around, and where `Hold()` puts it.
4. The header comment of each figure file states what it is, the units, the axes and where the origin is.

## Building shapes

1. Put every dimension in a named constant at the top of the file. Derive dependent sizes from them (for example `BODY_WIDTH = LEFT_PANEL + WHITE_COUNT * WHITE_WIDTH + RIGHT_PANEL`), so that changing one number keeps the parts aligned.
2. Use small helpers: `mesh()` creates a mesh and turns on `castShadow` and `receiveShadow`, and `box()` places a box by its bottom instead of its center.
3. Straight parts: `BoxGeometry`. Rounded parts: `RoundedBoxGeometry` from `three/addons/geometries/RoundedBoxGeometry.js`, with a radius smaller than half of its smallest side. Curved outlines (such as a grand piano case): a `THREE.Shape` drawn from above, then `ExtrudeGeometry` rotated so that it extrudes upward.
4. Repeated parts (keys, legs, pedals) share one geometry and one material. A part gets its own material only when it changes on its own (a pad that lights up, a knob with its own colour).
5. Build all materials in one `createMaterials(theme)` function, which takes every colour from the theme (see [Colour and theme](#colour-and-theme)). To change a colour, change the theme, not the figure.
6. A figure that has lots of empty space on one side (such as the left panel of a keyboard) keeps it on purpose, as room for controls added later. Don't fill it or shrink it without being asked.
7. **No decorations the user didn't ask for.** Build the object itself, not extras on it. The user removed both extras added so far: a face on the MIDI keyboard's left panel and a flag (pennant) on the boat's mast. **The user's word for a part may not be ours:** after the pennant was gone, "the boat still has a flag" meant the sail (a triangle on a pole reads as a flag), so the sail and its boom were removed too. Then "remove the pool in the boat" was a typo for pole: the bare mast went as well, and the boat is a hull with a rudder. When the user says a part is still there after it was removed, don't just repeat that it's gone. Check what they see (fetch the module from their dev server on 8087 via `localhost`, which listens on IPv6 only, and take a screenshot), then find the part that matches their word.
8. **Smooth, curved hulls and shells** (a boat hull) are built from a shape function of two numbers, `u` along the length and `t` around a cross-section, turned into a surface by `gridGeometry(rows, columns, point)` in `Boat/parts.ts`. Wind the grid so the triangles' front faces point out (see `Hull.ts`), and close an open end with a `Shape` of that end's cross-section (the transom). A low poly body that bends (the fish's kinds, from the user's models; Moving parts rule 10) is rings of a few corners along a line, each square to it at rest, joined by flat faces, closed to a point in front and flat behind. Its triangles are written again in place every frame as the rings move (`LiveFaces` in `Fish/parts.ts`), each with its own normal, and its fins grow from the rings' corners as strips, so they bend with it. (The smooth fish before them was a seamless `tubeGeometry` with extruded fins, both gone.)
9. **A thin shell has two sides.** Draw the outside with a front-side material and the inside with the same geometry and a `BackSide` material in another colour. Only the outside mesh casts shadows; if both do, each side shadows the other and the surfaces fill with fine stripes (shadow acne). A sheet with the same colour on both sides (a fish's fins, tail fin and teeth, a bird's wings, the lion's mane) is the same two meshes of one geometry: only the front casts, and it draws both of its faces into the shadow map (`shadowSide = DoubleSide`), since a front-sided material casts from its back faces, so a sheet whose front faced the sun cast nothing. The stage's normal bias keeps the lit side clean.
10. **Parts inside a curved shell** (a bench across a hull) are sized from the shell's tightest point where they touch, not their center: the hull narrows downward and toward both ends, so a bench as wide as the hull at its center pokes its corners out through the sides. Check with a raycast from each corner toward the shell. A `Raycaster` only hits the side of a surface its material draws, so cast against the inside mesh when the ray starts inside.
11. **Lines and cords** (fishing line) are drawn far thicker than real: the rod's line is an 8 mm cord, after the user asked twice for a thicker rope. They cast no shadow, and they are kept out of the Kuwahara filter with `keepSharp()` (see [Effects](#effects)), since the filter averages away anything a few pixels wide; that, more than the thickness, was why the rope kept looking thin. The fishing rod's line is tied just below the tip, where a band of wound line (the lashing) sits on the pole, and hangs from there. A hanging line is its own group at the point it hangs from, turned in `update()` so it points straight down in the world whatever way the figure is held.
12. **Textures are made in code**, like the shapes: no image files. `src/textures/woodGrain.ts` draws a wood-grain tile (planks 12.5 cm wide with seams, a butt joint in each, wavy growth rings and streaks) into a `DataTexture`, made once and shared. It is grey, so the material's theme colour shows through: `wood(theme)` in `theme.ts` is the theme's `wood` colour in its finish with that texture (the boat's planks, bench, rudder and tiller). One tile is 1 m, so give a textured surface **texture coordinates in meters, with u along the grain**: `gridGeometry`'s `uv` callback for a hull (u along the hull, v around it sized to the widest section, so the planks narrow toward the ends like real strakes), `grainUVs()` in `Boat/parts.ts` for boards, blades and rods (grain along the longest side), and a `ShapeGeometry`'s own coordinates, which are already in meters (the transom). The Kuwahara filter softens the grain but keeps the planks. **Bark** (`src/textures/bark.ts`) is the same idea for branches: ridges along the branch split by darker furrows, darker than the grain, so `bark(theme)` in `theme.ts` turns the theme's wood colour into bark and a cut end in the plain wood colour shows paler, like fresh wood. Its tile is 20 cm and tiles both ways, so give a branch texture coordinates in meters along it and exactly one tile round it: the bark wraps without a seam. **Soil** (`src/textures/soil.ts`) covers the lake's ground, as the user asked ("texture in ground surface"): lumpy earth (clods, crumbs, grit), pebbles 5 mm–3.6 cm each with a dark rim where it sits, and thin cracks in patches of dried earth. Its tile is 2 m, laid flat on the ground's x and z in meters. Its brightness is its height too (pebbles light and raised, cracks dark and sunk), so the same texture is also the ground's bump map. It is scaled so its average in linear light is `SOIL_MEAN` (0.7), and the ground divides by that, so the theme's colours stay the same on average. It takes about 0.25 s to draw, once per page load: per-pixel sRGB conversion through `THREE.Color` took 0.76 s, so it goes through 256-entry tables. **End grain** (`src/textures/endGrain.ts`) is what a sawn end shows: growth rings round the pith, wavy and crowding toward the bark, darker heartwood, a few drying cracks running in from the bark, and a rim of bark. It is one disk, not a tile: the pith in the middle and the bark's outside on the circle of radius 0.5. A cut face gives each point texture coordinates at its share of the way from the pith to the outline, in its direction from the pith (`cutGeometry()` in `objects/Log.ts`), so the rings follow any outline and an off-centre pith. At 512 px it takes about 0.13 s to draw; at 1024 px, with an iterator and a noise call per pixel for each crack, it took 0.65 s. Under the Kuwahara filter at preview distance the rings soften, leaving a pale disk with a darker heart and a dark rim. All the textures share the tileable noise in `src/textures/noise.ts`.
13. **Traditional, not modern.** The user found a spinning rod (reel, guides, foam grips) too modern and asked for one made from a tree branch (*ranting kayu*): a crooked, tapering pole with bark, cut ends and twig stubs, the line tied at the tip. At the user's request it is a stout branch (5.2 cm across at the butt, 1.8 cm at the tip) with small details that make it real: a side twig snapped and hanging from its splintered break, and a leafy twig and a leaf near the tip (leaves use the theme's `grass` colour, its foliage colour). The boat went the same way: its sail and mast came off and it became plain wood. For an everyday object, build the simple, traditional version (natural materials, hand-made, as it would be found in an Indonesian village) unless the user asks for modern equipment.

## Moving parts

1. Every moving part sits in its own `Group` whose origin is the **real pivot**: the back edge of a key, the hinge of a lid, the center of a knob. Then its rotation matches the real movement (for example, `rotation.x > 0` dips the front of a key).
2. Anything that turns around its own axis (a knob or a wheel) gets a visible marker (a white line or dot). Without one you can't see it turn.
3. The public API uses real-world terms: `setKeyPressed(midi, pressed)`, `setKnob(index, 0..1)`, `setPitchBend(-1..1)`. Clamp values to their range, and ignore out-of-range indexes and notes instead of throwing an error.
4. Setters only set a **target**. `update(delta)` moves each part toward its target with `t = 1 - Math.exp(-speed * delta)`, so the speed is the same at any frame rate. The caller calls `update(delta)` once per frame.
5. Ranges and counts are static fields (`LOWEST`, `HIGHEST`, `KNOB_COUNT`), so demos and other code read them from the figure instead of hardcoding them.
6. **One-shot and continuous behaviours.** One-shots (`Flap()`, `Jump()`) play once and end by themselves. Continuous ones (`Walk()`, `Run()`) keep going until another behaviour replaces them, so they need a way to end: the penguin has `Stop()`, added beyond its spec and reported to the user. Ease between states (standing, walking, running) with the same exponential easing as setters, so switching never snaps.
7. **A figure that walks moves itself.** It goes forward along its own +z at a speed that matches its steps, and exposes that speed (`penguin.speed`, in m/s). Callers steer by turning it (`rotation.y`); turning by `speed / radius` radians a second walks a circle of that radius at any gait. Jumps and other in-place moves stay inside the figure and never change its position.
8. **No sliding feet.** A planted foot must stay put on the floor. When each foot is planted for half a cycle and slides back one stride under the body, the forward speed is `2 × stride × cadence` (the animals' `stride × cadence / duty`, duty 0.5). Check it numerically, not by eye: run `update()` in small steps in Node (Vite's `ssrLoadModule`, [Checking the result](#checking-the-result) rule 8) and confirm a planted heel's world position doesn't move over a whole stance while the body does, and that it is on the ground all through the stance (a foot out of its leg's reach lands late or lifts early; Animals rule 4).
9. **Split a walking figure into a rig and a torso.** The rig (everything) takes the jump height and squash. The torso (everything above the feet) leans, bobs, rolls over the planted foot and twists, while the feet step on the floor beside it. The head can undo part of the torso's lean and roll so it keeps looking ahead, where it is a part of its own: the modelled penguin's head is one loft with its body (Animals rule 16), so it leans with it.
10. **A figure that swims moves itself in three dimensions.** The fish's `SwimOnSurface(direction)` and `SwimOnDepth(direction)` turn it toward the direction the short way round, send it forward along its own +z at `speed`, and raise or lower it to its depth, nose up or down. It takes the water's surface to be `y = 0` of its parent, as in the lake, and exposes its two heights (`fish.surfaceY`, `fish.depthY`). A `Direction` is in the scene's axes: `forward` +z, `back` −z, `left` −x, `right` +x; an unknown one is ignored.
    - **Three kinds, from the user's models** (2026-09-26). The user gave two three.js pages for the fish in `animals/Fish.md` ("Shape Reference (Salmon & Piranha)", one factory making both, and "Shape Reference (Nemo)", a clownfish) and chose: "Three kinds of the fish: the fish figure takes a kind; all three swim, dive and leap as the fish does; each gets a preview. The lake and the Hold menu use the salmon." `new Fish({ theme, kind })` takes `salmon` (the default), `piranha` or `clownfish`; the models' numbers are kept as written in `Fish/models.ts`, and a `unit` per kind makes the salmon 29.6 cm long (as long as the fish before it), the piranha 25 cm and the clownfish 10 cm. At rest each is its model, every triangle and colour to 0.00001 mm (the pages' own code run in Node). The models draw everything from both sides, wound inward; here closed surfaces face out and thin sheets are two-sided (Building shapes 9). Their page turns the tail fin toward a point it reads as a world point, which tilts it 66° up once the page's fish swims; here it follows the body's end. Colours: the salmon's blue-greys are the sky's and the water's colours darkened (its pink stripe never shows, as on its page: with eight corners no face sits in its band), the piranha's reds felt's rust (`autumn`), since felt has no red, and the clownfish's orange the `trim`, its white bands edged in dark. Each has a preview (`salmon`, `piranha`, `clownfish`, in the Figures tree's Fish folder), its square, leap and camera the salmon's times its size; `?figure=fish` now shows the default figure. 675–747 triangles in 11–14 meshes, built in about 1 ms; bending the body costs about 40 µs a frame (the smooth fish 1.8).
    - **Its distances and speeds follow its size** (`fish.size`, its length over the salmon's). The salmon's are the fish's before its kinds: 0.35 m/s; its back 1 cm under on the surface and 0.6 m down at depth; rising or diving at up to 0.25 m/s; a 35 cm run-up before a leap. A smaller kind's are smaller in proportion, and each swims faster by as much as its model beats faster (the pages' `swim.speed`): 1.2 lengths a second for the salmon, 1.6 for the piranha, 1.4 for the clownfish. Scaled so, every kind's preview square works as the salmon's does.
11. **Swimming motion follows the speed.** A fish moves 0.75 of its length per tail beat, so the beat quickens with speed and slows to a gentle idle while it hovers.
    - **The bend.** The body bends as its model sways it: from the model's `stillFrom` back, more and more toward the tail (the square of the share of the way), in a wave of the model's wavelength and amplitude at full speed, a quarter of that (`IDLE`) while hovering, never past the model's size: in a leap's burst only the beat quickens (at 1.8 times the model's sway, the bent tail and its flick turned the tail fin edge-on). The wave runs toward the head, as the models' does; a real fish's runs toward the tail.
    - **The rings** are built again round the bent line every frame (`Body.bend`), so the fins that grow from them bend too. Each ring is its rest ring turned about the upright by the way the bent line heads there, so bending moves nothing up or down: the models' own rings, square to the bent line, sank the piranha's lowest point 0.03 mm as it swayed, which broke a leap's exact clearance.
    - **The fins and turns.** The tail fin sits on the tail's end, facing the way the body runs there, and flicks as the model's does (0.35 rad at full speed); the head sways against the tail; the pectoral fins paddle as the models' do, about their middle angle 0.3 rad either way at the model's rate, half as far at full speed (part of each stroke takes them inside the body, as in the models). In a turn the fish leans in and bends its tail toward the turn, the tail's end turned by 0.25 × the turn rate.
    - **The pivot.** Pitch, lean and sway happen in an inner rig pivoted at the model's origin, the middle of the body, so the fish turns around its middle rather than its origin on the floor. Check a swim loop numerically (positions over time) as well as by eye: the fish demo's square stays in place loop after loop because each side ends where the fish crosses the square's edge. Timed sides kept it in place only until a leap carried the fish faster than it swims.
12. **A leap is planned, not steered.** `JumpOutFromWater(height)` works out the whole leap when it starts, so the fish clears the water by exactly `height`: at the top its lowest point is that far above the surface, which is `position.y = height`, since the origin is under the lowest point. The fish's middle leaves the water at 60° with just the up speed gravity needs, `√(2g × rise)`. Near the surface it first dives until its middle is 35 cm down (the salmon's; a smaller kind in proportion), to gather speed. Its up speed then grows with the square of the time (a cubic), so its nose turns up without a jolt. In the air it has nothing to push on, so it turns at a steady rate from nose up to as far nose down, level at the top. Unlike the penguin's jump, the leap moves the fish itself, since its height is part of where a fish is, and it holds its heading throughout. Swimming behaviours given in the air wait until it is back in, where drag above its swimming speeds slows it back to them. A second leap is ignored until the plunge back in has slowed. Where its middle breaks the surface, going out and coming back in, the fish sends a `splash` event with its velocity, and the preview hands it to `environment.water.splash` (see [Environments](#environments)). Check it numerically: `Box3.setFromObject(fish, true).min.y` at the top equals the height, the fish is level there, and position and speed change smoothly from frame to frame, at 240 fps and at 20, for every kind (checked 2026-09-26: five leaps each, the height to 0.0000 mm, two splashes each where the middle crosses the surface).
13. **Speech bubbles** (`src/speech/SpeechBubble.ts`, shared by any figure that talks; the penguin's `Speech(text)`): a comic bubble, a sprite that always faces the camera, in the theme's `light` with its outline and words in `dark`, sized in meters (text 3.2 cm, lines up to 34 cm) and drawn on a canvas at 1.6 px a millimeter. A bubble holds at most **nine words**, as the user asked (a word over 50 characters is first cut into 50-character pieces, each counted as a word; `splitSpeech()`); in a bubble the words wrap into lines up to 34 cm wide and the bubble is as tall as its lines, so a long piece makes a tall bubble. Bubbles pop up from the tail one after another, each staying about 0.8 s plus 0.06 s a character (at least 1.4 s), and saying something new cuts off the rest. The bubble hangs outside the rig, so a jump's squash never squashes the words, and rises with the jump. The stage frees a sprite's own texture when the figure goes; other textures stay, since some are shared.

## Environments

An environment is the surroundings a figure is shown in: so far the plain `floor`, the `lake` and `grass`, with more to come; the lake and the grass end in a border of cliffs, mist and tall grass (rule 19), under a sky with the sun and clouds (rule 21). The panel's Environments tab or `?environment=<name>` picks one, and the tab marks the figure's own. Until then each figure shows in its own (`figureEnvironments` in `src/previews.ts`: the boat and the fish's three kinds on the lake, the trees on the grass, the rest on the floor); a pick stays when the figure changes. An environment's land can be put together from [terrains](#terrains), the kinds of ground in `src/environtments/terrains/`: the lake's swamps are the first (rule 26).

1. Environments live in `src/environtments/<Name>/` (the folder is spelled as the user created it), built like a figure, with a spec next to the code: `Floor.ts` is one plane, `Grass.ts` a lawn, and `Lake.ts` puts together `Ground.ts`, `Water.ts` and what grows and stands on them. Every colour comes from the theme: bare land is `scene.floor`, the water `scene.water`, and lawns and grass `scene.grass`.
2. **Each environment has an entry in the `environments` table** in `src/previews.ts`, and the Environments tab lists them in table order. The entry builds the `scenery` and says where a figure goes: `land`, where a figure stands, and, if there is water, `water.at`, where a figure goes whose preview has `place: 'water'`, with `water.heightAt(x, z)` measured from there. The stage moves the scenery so that the figure's spot is at the origin, so figures, cameras and shadows stay put in every environment. It calls the environment's `update(delta)` every frame before the preview's, and frees it with the figure.
3. The origin is the center, at the level figures use: for the lake, `y = 0` is the still water surface, the bed is up to 1.4 m below it and the top of the bank 0.3 m above it; the land beyond is uneven (see rule 15). `lake.surfaceAt(x, z)` and `lake.groundAt(x, z)` give the heights at a point. Anything placed on the land stands at `groundHeight(x, z)` (`Ground.ts`), never at a fixed height. The swamps are dug into the land after everything else is placed and off all of it, so `lake.groundAt()` is the land as dug (rule 26).
4. **Floating.** A floating figure sits its draft below the water (`Boat.DRAFT`, 0.1 m) and rides the waves: sample the water's height (`environment.water.heightAt`) ahead, astern and on both sides, then ease its height, pitch (`rotation.x`) and roll (`rotation.z`) toward them with `1 - exp(-speed × delta)`, because a hull lags the water.
5. **Keep water out of hulls.** The water is a see-through sheet at the waterline, so it runs through anything that floats, and the inside of a hull looks flooded. `keepDry(root, materials)` in `src/environtments/water.ts` marks the inside surfaces (on the boat, the hull's `inside` material; anything standing inside a hull below the waterline, such as a mast's foot, needs marking too). They are drawn after the other solid meshes and write the stencil buffer where they are the visible surface, and the water (`waterSurface(material)`) is not drawn there. Never mark the outside of a hull, or its part under the waterline looks out of the water. This needs `stencil: true` on the renderer and `stencilBuffer: true` on the composer's target (both in `Stage.ts`).
6. **Waves** are a few sine waves crossing each other, each moving at the speed deep water gives its length (`ω = √(g·k)`), 1–3 cm high on a lake. One sum moves the water's vertices, sets their normals from its slope, and answers `surfaceAt`, so a floating figure follows exactly what is drawn.
7. **The ground meets the water at a slope**, not flat, so the waterline is a crisp line instead of a band that flickers as the waves wash over it. The lakebed fades from the floor colour toward the water colour with depth, so deep water looks deeper.
8. **A preview is built for its environment.** Its entry gets it, `(theme, environment) => Preview`, so a figure can behave differently with and without water: the boat floats when `environment.water` exists and otherwise rests on its keel on the ground. A figure that only stands needs nothing.
9. **A place to stand needs room.** `land` must be flat for the figure's whole footprint, and for a walking demo's circle. The lake's is `Lake.LANDING` (defined in `Ground.ts`, since the land is shaped round it), on the +z shore 1.5 m past the top of the bank, where the uneven land is kept level for 2.2 m round it. That leaves room for a figure about 3 m across, with the water behind it (toward −z), where the preview cameras look.
10. **To add an environment:** build it in `src/environtments/<Name>/` with its spec, add its entry to `environments` with a flat `land` spot (and `water` if it has water), and check a standing figure (the penguin) and, if it has water, the boat in it, from the preview's camera.

14. **Splashes** (`Lake/Splash.ts`, through `environment.water.splash(x, z, velocity)`): where something breaks the water's surface, drops fly under gravity until they fall back in, and two rings of ripples spread from the spot and fade over 1.6 s. Their points are set from `heightAt` every frame, 4 mm above the water, so they ride the waves. Leaving the water, 70% of the drops are dragged up after the thing at a share of its speed, so they trail behind it; coming in, all of them are thrown up in a crown. The splash grows with the speed: 50 drops at 3 m/s, a 30 cm leap. Drops are drawn far bigger than real (2–5 cm) and the rings 3–7 cm wide, because the Kuwahara filter averages away sparse small drops. Drops thrown out in a ring vanished by the top of the leap in a 1000×700 window, while dense clusters (a crown, a plume) read as painted spray. The drops are one instanced mesh and the rings a pool of eight, all in the water's colour lightened toward the theme's `light`. The rings are drawn after the see-through water (`renderOrder` 2, no depth write), or the water would cover them. The figure only says where it breaks the surface (the fish's `splash` event), and the water owns the splash, so the splash stays where it happened while the fish moves on.
15. **Uneven land round the lake** (`Lake/Ground.ts`), as the user asked: past the top of the bank the land humps and dips. 17. **Weather now and then** (`Lake/Weather.ts`), as the user asked ("fog and wind sometimes"). Fog rolls in over about 12 s, hangs 20–35 s and clears, 40–90 s apart. Windy spells of 12–25 s come 15–40 s apart and gust while they last, with only a breath of wind between them. The first fog comes 25 s after the lake is shown and the first wind after 8 s, so both are seen without a long wait; after that the times are seeded.
    - **Fog** is the scene's `FogExp2` in the theme's background colour. An environment can give `fog` (`Environment` in `previews.ts`), and the stage puts it in the scene or clears it. At its thickest it mostly hides the far shore, 20 m off, and hardly touches a figure 2 m from the camera; but a tree figure previewed on the lake from 25 m fades out while it lasts. Speech bubbles take no fog, so their words never fade.
    - **Wind** (`src/environtments/wind.ts`) is shared uniforms (time, strength, direction), and `sway(material, wind, { sway, reach })` bends a material's meshes on the graphics card, from each mesh's or instance's origin. A point moves `sway` m at `reach` m up, growing with the square of the height, with gusts running downwind and a quicker flutter. The sward sways 7 cm at 25 cm up, the meadow 22 cm at 1 m, and the trees' crowns 35 cm at 15 m. Only the drawing moves, not shadows or `heightAt`.
    - **The water roughens in the wind** (`Water.setWind`): its waves grow up to 2.2 times as high, a 90 cm ripple runs downwind, and the glint dulls. `heightAt` uses the same waves, so a floating boat rocks more.
    - **Checking it:** a still screenshot can't show the timing, since headless Edge's virtual time hardly moves the scene's clock. To look at fog or wind, shorten the first times and the easing in `Weather.ts` for the screenshot, then restore them. Compare a windy and a calm frame with the filter off: the tall stems lean downwind.

21. **The sky** (`src/environtments/Sky.ts`), on the lake as the user asked ("add sky in lake"), then on the grass too. The grass has no weather, so there the clouds drift toward +x and the sky never greys over:
    - **A dome drawn behind everything.** It moves with the camera (`onBeforeRender` copies the camera's position), is drawn first (`renderOrder` −1000), puts its points on the far plane (`gl_Position.z = gl_Position.w`, as three.js draws a background) and neither tests nor writes depth, so it needs no size and nothing can come in front of or behind it wrongly. Its colour is worked out per pixel from the direction. At the horizon, and below it, it is exactly `scene.background`, the colour the land fades into at its end (rule 19) and the fog's, so the land still meets the sky with no line. Going up, it deepens to the theme's `zenith` (`1 − (1 − sin elevation)⁴` of the way: 30% at 5°, 54% at 10°, 94% at 30°), which a curve rising slower would leave almost unseen, since the low preview cameras show only the sky's lowest few degrees. Colours are mixed in linear and converted for the screen (`colorspace_fragment`) as the background is, never tone mapped.
    - **The sun** is where the key light shines from: `SUN` in `src/sun.ts` is shared by the stage (`fitShadow` puts the light out along it) and the sky, so shadows fall away from the drawn sun. It is a disc 3.6° across in the theme's `light`, with a glow round it. It sits behind the preview cameras, about 50° up, so it shows only when the view is turned.
    - **Clouds are the [cloud object](#objects)**, five shapes built 2 m wide (21 k triangles, the least its clumps allow; the default is 47 k) and drawn as sixty meshes sharing them, each stretched to 150–320 m wide and turned its own way, 220–340 m up and up to 2.5 km out, so they cover about 8% of the sky. Each mesh is frustum-culled on its own, so only those in view are drawn. They drift downwind at 6 m/s (`wind.direction`), and one that drifts out past 2.5 km downwind comes back in on the far side. They fade into the sky behind them (the dome's own colour that way, so a faded cloud vanishes), 15% even near and all the way between 1 and 2.4 km from the camera, so they come and go unseen. The sky lights them from all round (emissive: half the zenith's colour), since the stage's lights left their undersides as dark as a storm cloud's. The camera sees 3 km (`far` in `Stage.ts`; it was 100 m).
    - **What failed first:** clouds 60–140 m wide and 90–150 m up. From the landing the cliffs stand 10–25° high and hide the far, low clouds, so only clouds a few hundred meters off show above them, and at that size the sky looked empty.
    - **Fog greys the sky over.** The clouds take no scene fog (it would hide them long before the sky); the dome and the clouds mix toward the fog's colour as much as the fog greys a thing 30 m off, so at the weather's thickest fog the sky is the flat fog colour, clouds and sun gone, as before.
    - **Cost:** 45–90 ms to build (the lake builds in about 0.7 s with it, the grass environment in about 95 ms, 47 ms before). On the graphics card the lake meeting and the oak tree on the grass held 60 frames a second; in a run while the machine was busy, the lake drew 42 frames a second with it and the plain floor 46.
    - **Checking it:** the preview cameras look down at the figure, so walk the camera (`?camera=walk`) and hold its moves from the test script by importing the page's own module: `import('/src/walk.ts').then((m) => m.press('lookUp', 'test'))`, then `release`. The walker starts looking about 41° down at the figure; `lookUp` turns 60° a second and `turnRight` 90°. A tree's preview shows the most sky from a preview camera (`?figure=oak-tree`, on the grass or the lake).
22. **Day and night at the lake** (`Lake/DayNight.ts`), as the user asked ("in lake add day and night, and if night, add firefly"). Only the lake has night; the floor and the grass stay in day.
    - **They take turns on their own:** 6 min of day, a minute of dusk, 4 min of night and a minute of dawn, easing between (smootherstep). The first dusk comes a minute after the lake is shown, as the first fog comes soon. The **Time of day** setting (the Environments tab, `?time=cycle|day|night`, `cycle` leaving no parameter) holds it at day or night instead; a change eases there over a few seconds, and a lake built with `?time=night` starts at night. It goes to the stream's hidden page with the other settings.
    - **What night is:** the lake as it is by day, darkened. Each theme has `scene.night` (sky at the horizon and overhead, the two hemisphere colours, the key light, and their intensities; [Colour and theme](#colour-and-theme) rule 3), and `sceneAt(theme, night)` in `theme.ts` mixes the day's values with them. The key light turns moonlight from the sun's direction, so shadows stay put. The sun fades out over the first half of dusk and back over the last half of dawn (`skySunShow` in `Sky.ts`). The clouds' skylight follows the zenith, and the water's glint dulls (`Water.setNight`). There is no moon and there are no stars, since the user didn't ask for them. Dim, not black: the penguin at the landing still reads at night.
    - **The stage keeps its lights.** The environment says how far into the night it is (`Environment.dayNight`, next to its `fog`), the stage mixes its background, hemisphere and key light from it every frame (`applyDaylight()` in `Stage.ts`), and the Time of day reaches the environment through `stage.setTimeOfDay()`, which also hands it to every new environment before its first frame.
    - **Colours baked at build time had to follow.** The land's fade into the sky at its end (`haze.ts`) was a constant in the shader, and part of the program's cache key. It is now a uniform: a `THREE.Color` given to `hazeEdge()` is followed as it changes, any other colour stays fixed. The lake keeps one horizon colour, shared by the ground's fade, the border's grass, the fog, and the border's cliffs and mist (`BorderOptions.sky`), which re-tint themselves from it every frame in `Border.update(delta, night)`. A cliff's rock and scree share one material, which the old build-time loop hazed once per mesh, so it is hazed by `1 − (1 − 0.18)²`: the day looks exactly as before. The mist is lightened toward `light` by 35% by day but 12% at night, or it glowed against the dark sky.
    - **Checked:** in Node, over a cycle and a half with the setting switched on the way, the largest change in a frame is 0.014 of the way to night, 3 of 255 in the sky's colour and 0.02 in the key light's intensity: no jumps. Dusk starts at 1 min and night lasts 4 min. In the browser, clicking the Time of day's `night` writes `?time=night` and eases the lake to night in about 4 s, `cycle` takes the parameter away and eases back, and `?time=night` on the floor or the grass changes nothing.
23. **Fireflies at night** (`Lake/Fireflies.ts`): twenty of the firefly object ([Objects](#objects) rule 7) over the grass on either side of `Lake.LANDING` and in front of it, where the preview cameras look, 0.3–2 m above the ground, and four over the water's edge. They come out at dusk and go at dawn, their lanterns fading in (`Firefly.lit`).
    - **Built once and hidden by day** (`visible = false`: nothing is drawn or moved). They are drawn once in the first frame whatever the time, lanterns and halos dark, so their materials compile with the lake's: compiled at the first dusk, they froze the page for 0.2 s.
    - **They wander in their own areas.** Each flies forward at 0.25–0.45 m/s (its `speed`: the 4 cm/s it first walked at as an animal looks frozen from meters away) and is steered by turning it, as the animals' demo steers them. It turns in waves of its own, and the nearer it comes to the edge of its area (1.2 m round its home) the more it turns back home instead, at up to 3.5 rad/s. First the pull was a fixed push added to the wandering, which the wandering outweighed: a firefly strayed 4.3 m from home and flew within 0.22 m of the landing. Now it strays at most 1.56 m (its turning circle), and turns away from the landing as it comes within 2.6 m of it, never nearer than 1.8 m. It rises and sinks on its own slow wave, placed by its height (`Firefly.HOVER` below its body). Each flashes on its own timing (`FireflyOptions.seed`: a start in its cycle, and a flash up to 12% faster or slower), so at most a third flash at once.
    - **No lights** (`FireflyOptions.light: false`): the lake is the heaviest scene, and a light costs every lit surface in it. So the number of lights is the same by day and by night.
    - **Visible from meters away.** A 2 cm firefly 5 m off is a pixel or two, and the Kuwahara filter took it. Each lantern is `keepSharp()`, and a halo sprite in the glow colour, 16 cm across and brightest in the middle, shines round it, brighter at each flash. The halo adds its light without touching the picture's alpha (`CustomBlending` with `blendSrcAlpha: ZeroFactor, blendDstAlpha: OneFactor`), since the filter reads alpha under 0.9 as "keep sharp": with normal blending, the halo over the lantern raised its alpha back past 0.9. At 6 cm with a steep falloff the halos were 2–3 px dots.
    - **Cost:** 60 frames a second by day and by night on the graphics card, and 0.6 either way in SwiftShader with the filter at 1000×700 (the lake itself is that slow there). The fireflies in view add about 90 draw calls (182 to 275), 3 k triangles and 4 shader programs.

## Terrains

The kinds of ground an environment's land is put together from, as the user asked ("environtments/terrains its base that can use in environtment like lake and other"): so far `GrassTerrain`, `MudTerrain`, `WaterTerrain`, `SandTerrain` and `SwampTerrain` (the user's "add swamps terrain"), in `src/environtments/terrains/` (lowercase, as the user created it), one file per terrain next to its spec, with what they share in `parts.ts`. Their specs are drafts written from the code. The lake's swamps are the first an environment uses ([Environments](#environments) rule 26); the lake still has its own ground, water, sward and mud pits.

1. **A terrain lies over the land; it doesn't shape it.** The environment gives the land's height (`heightAt`, in the terrain's own coordinates; flat by default) and says where the terrain lies (`mask`: 1 where it is all that terrain, 0 where there is none, soft between; by default an uneven oval filling its footprint, `ovalMask()`). The terrain covers that land with its own surface, 1.2 cm above it (`LIFT`) where it is all that terrain and 1.5 cm under it (`SINK`) at its edge, so it meets the land in a line with no gap, as the mud pit's edge does. Where two terrains overlap, the higher shows. Water fills the land's hollows: its origin is on the still surface, so the land must be below 0 where there is water and rise above it all round inside the footprint, which hides the sheet's edge.
2. **Sized and seeded like the objects:** `new SandTerrain({ theme, seed, width, depth, heightAt, mask })`, each with its default footprint (`SIZE`: 10 × 8 m; the mud 8 × 6 m), which the default outline fills exactly. Every terrain answers `heightAt(x, z)` (its top: the lawn, the mud, the sand, or the water's surface now), `covers(x, z)` (its mask, to keep other things off it) and `update(delta)` (the water's waves; the others do nothing).
3. **One surface each, on a grid** (`surfaceGeometry()`): points 15–25 cm apart over the footprint, each painted by the terrain (its height over the land, its colour, how much of its texture shows and how wet it is), leaving out the cells the mask leaves out. One material does them all (`surfaceMaterial()`): the vertex colours, the texture showing as much as each point's `soil` says and divided by its mean so the colours hold on average (as on the lake's ground), its bumps shrinking with it, and a sheen where `wet`.
4. **Grass** (`GrassTerrain`): a lawn (the grass colour at 0.6, mottled ±12% in meter-wide patches, the soil showing 30%) under tufts of the sward's three shapes (`tuftGeometry` from `Lake/Sward.ts`), 7–26 cm tall and mostly short, 70 a square meter, kept as often as the square of the mask so they thin out before the edge, each leaning with the slope and bending in a `wind` as the sward does; `height`, `density` and `keepOff` change them. **Darker than the lake's lawn:** at the lake's shades (lawn 0.75, tufts 0.72–1.05) the tufts merged into the lawn under the painterly filter from more than a few meters off; the lawn at 0.6 and tufts at 0.8–1.15 keep them as strokes. About 3,600–3,900 tufts, 140–150 k triangles, 4 draw calls.
5. **Mud** (`MudTerrain`): the mud pit's mud as open ground, with no rim: the floor colour at 0.42 where wet to 0.95 where dry, wet through over half to four fifths of it in patches 2.6 m across and drying toward its edge, lumpy (3 mm where wet, 1 cm where dry), with a sheen where wet. Its puddles (about one per 8 m², `puddles`) lie where the mud is wet all round them, each a sheet in the water colour 4 mm above the mud over an 8 mm dip, so the mud under a puddle stays 4 mm above the land: at the land's own level it would flicker through the water.

## Trees

The tree figures live together in `src/figures/Tree/`, one file per kind next to its spec: `OakTree`, `CedarTree`, `MapleTree`, `PineTree`, `ChestnutTree`, `SpruceTree`, `ElmTree` and `WillowTree`, shown in the preview as `oak-tree` … `willow-tree`. The user's specs are empty so far (so are `BirchTree.md` and `PoplarTree.md`, which have no figure yet), so the trees have no behaviour and stand still.

1. **A family in one folder.** The kinds share their parts: `Trunk.ts` (the trunk and every branch in bark, one merged mesh), `Crown.ts` (every clump of leaves or needles, one merged mesh), `skeleton.ts` (growing the wood) and `parts.ts` (materials, the seeded random generator, limb and clump geometry). A kind's file only says its habit. Each tree exposes `tree.trunk` and `tree.crown`, with the tree's origin.
2. **Real size**, 10–21 m tall, with the origin on the ground at the foot of the trunk and the roots flaring a little below it. The tree preview (`tree()` in `previews.ts`) stands the camera back from the tree's middle by its height and width, so each tree is seen whole. Trees start on `grass`: behind a tree that size the floor's 20 m square shows its edges.
3. **Branches grow by space colonization.** Points are scattered through the crown's shape, and branches grow toward them in steps of 0.4–0.45 m, each point dropping out once a branch comes within its kill distance. A kind gives its habit: the trunk and first big limbs drawn by hand (`fan()`: an oak's low, wide limbs, an elm's vase of stems, a cedar's leaders), the crown's shape (an oak's broad, lumpy dome, a maple's egg, a chestnut's dome hollowed from below, an elm's umbrella open underneath, a willow's low dome, a pine's clouds round the top of a tall bare trunk, a cedar's flat layers), and how branches bend (`tropism`: up, or down beyond a radius, for a drooping rim). Radii follow the pipe model (a branch's r^2.5 is the sum of its children's), scaled to the trunk's radius. Without hand-drawn limbs, points all round one node pull it equally every way and it grows a single central leader, so a vase needs its stems drawn. The spruce is regular enough to build directly: whorls every 60 cm, branches shortening upward, drooping and turning up at the tips, each with a pad of needles.
4. **Leaves are clumps**: lumpy blobs (a sphere dented by a few random waves), shaded per vertex (the underside, and the bottom and inside of the crown, darker), a little past each twig tip, flattened for a pine's tufts and a cedar's shelves, stretched along a spruce's branch. The willow's curtain is cascades of tall, narrow clumps hanging from its outer branches and flaring out as they fall. Thin ribbons (like grass blades) were tried first and read as streaks under the Kuwahara filter; clumps keep the willow in the same hand as the other trees. Leaves are the theme's `grass` colour, darker for conifers (`FOLIAGE_SHADE`); bark is its `wood` colour through `bark(theme)`. **In autumn** (`autumn: true` in `TreeOptions`, which every kind passes to `createMaterials`) the leaves are the theme's `autumn` colour instead. Each clump takes a tint at random: the autumn colour (3 in 7), 40% toward `wood` for browner leaves (2 in 7), lightened 1.25× for faded leaves (1 in 7), or 45% toward `grass` for leaves still green (1 in 7). So the crown is mottled like a real tree in autumn. Mixing toward the theme's `light` colour for faded leaves made nearly white clumps in the dark studio theme (since dropped), so they are lightened instead. A tree grown without `autumn` draws the same random numbers as before, so it keeps its shape.
5. **Seeded.** `new OakTree({ theme, seed })`: the same seed always grows the same tree, and each kind has its own default. A loop that shrinks something each step needs a count cap besides its end test: the willow's cascades shrink by 0.9 a clump, which for some seeds converges above the hem, and without the cap it ran out of memory. Before placing trees with random seeds, build every kind with many seeds; Vite's `ssrLoadModule` builds figures in Node, without a browser.
6. **Cost.** A tree is two draw calls and 20–80 k triangles, and builds in 10–60 ms (the willow, with the most clumps, is the slowest). The clump sphere is made once and cloned.

1. **Every grass can be sized**, as the user asked: `new TimothyGrass({ theme, seed, height, width })`, in meters, each kind with its own default (`TimothyGrass.SIZE`). With only a height it keeps its shape. A plant is planned first as lines and blobs (leaf midribs, stem axes, clusters of spikelets, woody stems), and `fit()` in `parts.ts` stretches its heights and spreads to exactly that size, and its widths and radii only by the square root of the mean stretch, so a plant twice the size has leaves 1.4 times as broad, not twice. A wider plant also grows more leaves and stems (`crowd`). Blobs grow by that root and not the height, so `fit()` measures the sized plant in a few passes. Check sizes numerically: the built figure's box is within millimeters of the size asked for. Parts may share a point (a spikelet on the tip of its stem), so `fit()` scales each point once: scaled twice, a fescue asked to be 1.1 m came out 2.5 m tall.
2. **A family in one folder**, like the trees: `Leaves.ts` and `Stems.ts` (the parts, each one merged mesh; `Stems` adds a bark mesh for woody stems), `habit.ts` (tufts of leaves, flowering stems with their leaves, arching lines), `grow.ts` (plan, fit, build) and `parts.ts` (options, materials, colours, and the blade, tube and blob geometry). A kind's file only says its habit and its seed head. Each plant exposes `plant.leaves` and `plant.stems`, with the plant's origin on the ground at the middle of its foot.
3. **Leaves are ribbons** here, not clumps: blades along an arching midrib, folded into a V (keeled), each drawn front and back with its own normals leaning up, so either side is lit like the rest of the tuft. Seen from a meter or two they read as leaves, unlike the willow's ribbons seen from 30 m. Stems and seed heads are tubes (timothy's blunt cylinder, foxtail's soft spindle, Bermuda's fingers), roughened by `bumps`. Clusters and florets (cock's-foot, fescue, the chives' pom-poms) are the trees' lumpy clumps.
4. **Thin parts are drawn thicker than real**, as with the fishing line: stems 5–7 mm across, fescue's leaves 3 mm, rosemary's 5 mm. At real thickness the Kuwahara filter wiped out the stems, and the seed heads floated. Rosemary first looked like a bundle of brown sticks: thinner stems and denser, longer leaves made it a green bush.
5. **One material, coloured per vertex**: white in the theme's finish, times vertex colours taken from the theme (`palette()`). Leaves are `grass`, darker at their feet; seed heads ripen toward `wood` (straw), some with a touch of `flower`, as real ones are tinged purple; fescue's feet go toward `wood` (its red sheaths), and rosemary's undersides toward `light`. The chives' flowers are `flower`. Rosemary's stems are bark through `bark(theme)`.
6. **They start on the floor**, not the lawn, where their green disappears into the lawn's. The preview (`plant()` in `previews.ts`) takes in the whole plant, a little from above.
7. **Cost.** A plant is two draw calls and 10–85 k triangles, the most for Bermuda's mat and rosemary's needles, and builds in 5–100 ms. Blobs under 2 cm (spikelets, florets) use an 80-face sphere, not 320 (`clumpGeometry` in `Tree/parts.ts` takes a detail).
8. **Detail for plants seen from afar.** `detail` in `GrassOptions` (1 by default) is the share of leaves, stems and runners a plant grows. Under 1 the plant is also coarsened (`coarsen()` in `parts.ts`): blades keep every other point, and tubes get rings twice as far apart and fewer sides. At 0.2, timothy falls from 13.6 k triangles to 1.1 k and Bermuda from 62 k to 6.5 k. The lake's meadow uses it (see [Environments](#environments) rule 16).

## Stories

A story plays a scene: its figures in its own environment, moved by a script or by outside input. The panel's Story tab or `?story=<name>` plays one, and `none` goes back to the picked figure. While a story plays, the figure tree and the environments are greyed out with a note saying why, and keep their picks.

1. **A story lives in `src/story/<name>/`**, next to its spec `<name>.md`, which belongs to the user like a figure's spec. The folder and file names are snake_case, as the user named the first one (`piano_play`). Its code, `<name>.ts`, exports a `Story`: `{ environment(theme) => Environment, create(theme, environment) => Preview }`. The story builds its own environment: an entry of the `environments` table (`environments.grass`), or one made for it (the lake meeting's lake, with a wider clearing), defined once at module level, since the stage skips a `show()` whose builders are unchanged. Register it in the `stories` table in `src/stories.ts`; the Story tab lists them in table order.
2. **A story that listens to outside input stops in `dispose()`.** The stage calls a preview's `dispose()` when it replaces it, before freeing it. Without it, a story left behind would still act on messages.
3. **OSC (Open Sound Control) comes through the dev server.** Browsers can't receive UDP, so `osc-bridge.ts`, a Vite plugin, listens on UDP port 57121 (`OSC_PORT` to change it) on this machine only (127.0.0.1 and ::1). It also takes OSC over HTTP: `POST /__osc` with one packet as `application/octet-stream`, answered 204, or 400 with the reason. That route works from anywhere the dev server can be reached, through ngrok or a VS Code tunnel. It reads OSC 1.0 messages and bundles (a bundle's time tag is ignored: messages play as they arrive) and passes each message on to the page as the Vite event `osc:message`. In the page, `onOsc(listener)` in `src/osc.ts` listens and returns the function that stops. Only `npm run dev` has the bridge, not a built page. It logs once where messages come from, and warns about a packet it can't read.
4. **Vite starts a restarted server before it closes the old one**, when a config file changes. The bridge therefore opens its port once the new server is listening; opened at once, it found the port still taken (`EADDRINUSE`) and OSC stopped until a manual restart.
5. **`piano_play`**: the MIDI keyboard on `grass`, playing what OSC sends it. `/piano/chord "Am"` calls `PlayChord`, `/piano/note "E5"` or a MIDI number (`76`) calls `PlayNote`, and `/piano/release` lets go of every key. A chord or note stays down until the next one replaces it. A name the piano can't read is reported with `console.warn` and skipped. From Sonic Pi:

   ```ruby
   use_osc "localhost", 57121
   live_loop :piano do
     osc "/piano/chord", "Am"
     osc "/piano/note", 76
     sleep 1
   end
   ```

6. **Check a story with real OSC packets.** Start the test server with its own `OSC_PORT` (the user's dev server holds 57121) and send UDP packets from a small Node script, to 127.0.0.1 and to ::1. In the page, spy on what arrives by importing the same module (`import('/src/osc.ts')`) and calling `onOsc` from a DevTools `Runtime.evaluate`. Read the console warnings, and look at a screenshot for the pressed keys. After the story is switched off, a bad message must give no warning, which shows `dispose()` ran.
7. **Send OSC from the dev server's machine.** `npm run osc -- /piano/chord Am` sends one message, and `npm run osc:demo` plays a chord progression with a melody until Ctrl+C (`osc-send.ts`; `OSC_PORT` picks the port). UDP doesn't go through VS Code Remote Tunnels (a request for it was closed as not planned) or through ngrok, which both carry only TCP. So when the preview is reached through a tunnel, send from VS Code's terminal, which runs on the dev server's machine. For Sonic Pi on another computer, run `osc-relay.mjs` there (Node 18+, no packages; download it from the dev server at `/__osc/relay.mjs`): `node osc-relay.mjs <tunnel URL>`. It takes UDP on that computer's port 57121 and posts each packet to `/__osc`, one request at a time so nothing is reordered. Packets that arrive while a request is on its way go together as one OSC bundle. Sonic Pi then uses `use_osc "localhost", 57121`, as in `examples/sonicpi.rb`.
8. **Stop a test's child processes by PID.** On Windows, `child.kill()` on a process spawned with `shell: true` kills only the shell, and `npm run osc:demo` kept playing, holding the test's output open. Find it by its command line (`osc-send.ts --demo`) and stop that PID; never stop every `node.exe`. A Chocolatey-installed tool such as ngrok runs as two processes, the shim in `chocolatey\bin` and the real program in `chocolatey\lib`, so stop both.
9. **Playing by hand.** A preview whose figure can be played by clicking gives `press(part)`: it presses the part under the pointer and returns the function that lets it go, or null for a part that doesn't press. `piano_play` presses the key `MidiPiano.keyAt(part)` names. The stage listens for `pointerdown` in the capture phase, so it runs before the orbit controls' own listener. On a press it calls `stopImmediatePropagation()`, so holding a key and moving never turns the view, and it captures the pointer so the release arrives wherever the pointer lifts. Each pointer holds its own key, so two fingers play two keys. Anywhere else, dragging turns the view as before. To test, project a key's top face through the story's camera to find it on screen, press it with DevTools `Input.dispatchMouseEvent` or `dispatchTouchEvent`, and check a screenshot.
10. **A story can move the camera itself** (`Preview.shot()`): the stage follows its shot every frame while the view is the figure's own (`figure`), gliding (`SHOT_EASE`, most of the way in a second) or cutting when the shot says `cut`. Taking hold of the view (the orbit controls' `start`) makes the view free, as dragging does, and picking "figure's own" again hands it back; picking a direction or walking hands the camera to the viewer too. **Something new to show claims it back** (`Shot.claim`, `Stage.claim()`), as the user asked after bubbles were unreadable from a view dragged far out (from the wide shot the words are 3–7 px, from 20 m under a pixel). While the viewer has the camera, the stage still asks the story for its shot every frame, and when the shot claims the camera the view is the figure's own again and the settings are told, so the menu and the URL follow. It waits while the view is held (a drag, or turning the walking view) and claims it once let go. From more than 6 m off (`CLAIM_CUT`) it cuts: the story's 1.2 s glide would still be short of the speaker, and would fly through trees. Checked in a browser session through the remote-debugging protocol, reading the camera through a wrapped `Camera.updateMatrixWorld` and the menu through the page's settings module: a drag and zoom 21 m out, a picked direction, walking 21 m off (a cut) and a held drag (the camera stayed the viewer's for 6 s and came back half a second after letting go).       - Each circle must be over water deep enough that the log's underside keeps 25 cm off the bed. The bed is a bowl, so the circle's rim is enough to check.
      - It keeps 40 cm off the boulders and the dock (`nearDeck()` in `DockSite.ts`), and 30 cm off where the fish goes (`fishGoes`). Twice as many points go round that circle, since a box's corner can reach in between.
      - Between two logs only their eddies count, as the wind pushes them alike (the closest two came stayed the same in runs with two different pushes). Counting each log's full drift toward the other, with 1 m of it, found room for two logs.
    - **Where they are:** the fish's loop and its corridors take the near half of the water, the dock the far right and the boulder the west. Seed 6 puts all four where the cameras look: three in the far left water, one off the east bank. Of 30 seeds, 10 placed four; the rest three or two.
    - **The camera:** a log is solid for the meeting's cameras. `Sight.blocked()` asks `Logs.contains()`, whether a point is in a log's box where it has drifted to now; it can't go in the precomputed cubes, since the logs move.
    - **Checked in Node** (30 min, 8 viewers and the bots, the weather's own wind: over 0.5 in 24% of the frames):
      - every part of every log stayed over the water, at least 49 cm off the bed, 2.1 m from the shoreline, 1.8 m from the dock, 1.4 m from a boulder and 3.3 m from the fish's loop, never over where the fish goes, and 1.29 m from another log;
      - at its middle, 45% of its thickness under the water on average (24–67% as the waves pass along it);
      - at most 0.37 cm of height and 0.39° of pitch or roll in a frame, rocking more in wind (roll 0.43° against 0.73°, height against the water 1.3 against 2.1 cm);
      - it strayed up to 0.48 m from home, at up to 3 cm/s;
      - nothing was NaN, the camera was never inside a log, and no log came between it and the animal it followed.
    - **Checked in headless Edge:** the opening shot, calm and in wind, and at night; a log close up at the waterline, felt and studio, filter off and on, by day and at night; one end on, its round underside showing through the water.

## Keyboards and pianos

1. **Tuts** means keys. A keyboard includes its sharps (black keys) unless the user explicitly asks for white keys only. One octave = 7 white + 5 black keys, and two octaves (C4–B5, MIDI 60–83) = 14 white + 10 black keys.
2. Build keys by looping over MIDI note numbers. A note is black when `note % 12` is 1, 3, 6, 8 or 10. A black key is centered on the boundary between the white keys on either side of it.
3. Real sizes: a white key is 23.5 mm × 150 mm, and a black key is 13.7 mm × 95 mm, sitting about 1 cm higher. The key pivot is the back of the key.
4. A cute/toy keyboard may use wider keys for a chunky look (the MIDI keyboard uses 30 mm white and 17.5 mm black keys). Scale black keys by the same ratio as the white keys, and note the choice in a comment next to the constant.

## Colour and theme

Every colour comes from one theme, `felt` (`src/theme.ts`), named by role. There were six: felt, the getresolved.id brand's two (`getresolved` and `getresolved-dark`), `pastel`, `purple` and `studio`, picked in a Theme menu on the Settings tab or with `?theme=`. The user dropped all but felt on 2026-09-26 ("just keep felt, we dont need other"), and the menu and `?theme=` went with them; an old `?theme=` in a URL is ignored. The roles stay, so no figure hardcodes a colour, and a palette could come back without touching the figures.

1. **No figure hardcodes a colour.** Every colour comes from the `Theme` in `src/theme.ts`. A figure takes `{ theme }` in its constructor (default `defaultTheme`, which is felt) and builds its materials from it in a `createMaterials(theme)` function.
2. **Colours are named by role, not by object:**

   | Role | Used for |
   |---|---|
   | `body` | main surface, the palette's main colour (black in felt) |
   | `trim` | secondary surface: feet, rims, panels |
   | `light` / `dark` | light and dark neutrals: white and black keys |
   | `ink` | small details drawn on `body` (printed marks, labels) |
   | `marker` | indicators on knobs and wheels |
   | `metal` | metal parts: plates, pedals |
   | `wood` | bare or varnished wood: planks, benches, a rudder (shaded by the wood-grain texture) |
   | `fur` | an animal's coat, which each animal mixes with `trim`, `light` and `dark` into its own (see [Animals](#animals)) |
   | `accent` | every control (knobs, pads, buttons) |
   | `glow` | something that gives off light, drawn emissive so it shows exactly this colour: a firefly's lantern, a warm yellow in felt |

   A new figure maps its parts onto these roles. Add a new role only when no existing one fits, and give it a colour in felt.
3. **The scene belongs to the theme too.** The background (a warm grey), `zenith` (the sky straight overhead, a muted sky-blue; a sky deepens to it from the background at the horizon), floor, `water` (a lake's surface, a muted grey-blue; see [Environments](#environments)), `stone` (lakeside rocks: a warm grey darker than the floor, so they stand out from it), `sand` (loose sand, such as a beach's, [Terrains](#terrains) rule 7: a muted sand-beige, warmer and a little lighter than the floor, so it stands out from it too), `grass` (a lawn's blades, and any foliage: a muted sage green), `flower` (blossoms, such as chives' flower heads: a lilac that stands out from `grass`), `autumn` (leaves turned in autumn: a rust-orange that stands out from `grass`), the hemisphere light (`sky`, and `ground` for the bounce off the floor) and the key light all come from `theme.scene`. **At night** (`scene.night`, for the lake's day and night, [Environments](#environments) rule 22) the sky, the hemisphere light and the key light, now moonlight, have night values: a dusky blue-grey horizon under a navy zenith, and a pale blue moon.
4. **Pairs that sit on top of each other must contrast:** `ink` on `body`, `marker` on `accent`, `dark` on `light`. A white marker on a yellow knob is hard to see, and a theme that had `ink` = `body` (both black) lost every detail drawn in `ink`.
5. **A real brand's rules come first,** if one is brought in again: take its colours from its own source (guideline and design tokens), record them in a `brand_<name>.md` doc next to this one, and map them onto the roles there. [brand_getresolved.md](brand_getresolved.md) did this for getresolved.id, whose two themes were dropped with the others. Rules 6 and 7 below only apply to a palette designed from scratch.
6. **Build a palette from one hue in steps.** When designing from scratch, make a scale from 50 (palest) to 900 (darkest) and assign it: 50 background, 100 floor, 200 ground light, 400 body, 600 trim, 800 dark, 900 ink and marker. The dropped `purple` theme was built this way, from one violet.
7. **Exactly one accent colour.** Only one hue may sit outside the palette's own: a brand's chosen accent, or else the colour opposite its hue on the colour wheel (yellow for violet, mint for pink). Felt's is the orange of the penguin's beak and feet. Every control uses it, so all knobs have the same colour. Don't add extra colours for variety; three different knob colours (yellow, teal, pink) broke the palette. `metal` and `wood` may sit near the accent, since both are natural materials.
8. **Colour-accurate rendering: no tone mapping.** `applyRendererTheme` sets `outputColorSpace = SRGBColorSpace` and `toneMapping = NoToneMapping`. Hex values are sRGB, and a lit face shows its hex value times its shading. Neutral tone mapping was used first, but measuring showed it turns the getresolved brand's indigo `#4F46E5` into `#3224CE`, because it darkens low colour channels and oversaturates colours like indigo. With no tone mapping, it renders `#4941D3`. Keep light intensities in the theme so that colours don't drift between scenes.
9. **Measure, don't eyeball.** After changing the theme, the lights, the rendering or a surface's colours, screenshot the scene and sample the pixel colour of the main lit faces (for example with `System.Drawing.Bitmap.GetPixel` in PowerShell). Compare them with the hex values, and write the measured values down with the change (the swamp's are in [Terrains](#terrains) rule 8).
10. A lit surface is never exactly its hex value, because light and shade change it. When a colour has to match exactly (a logo, a flat colour patch), use `MeshBasicMaterial`, which is unlit.
11. **One theme.** There is no Theme menu and no `?theme=`. Figures and environments still take `{ theme }`, and the stage still shows every preview in one (`show(preview, environment, theme)`): always `defaultTheme`, felt.

## Cute style

The MIDI keyboard shows this style. When the user asks for "cute":

1. Round the edges, but only a little. The user found a 12 mm body radius and 5 mm key radius "too bubbly". The accepted amount is **6 mm on the body, 2.5 mm on white keys and 2 mm on black keys**, with a 1.5 mm gap between keys.
2. A soft palette: it was the `purple` or `pastel` theme, both dropped on 2026-09-26. With felt the only theme, ask the user before giving a cute figure colours of its own.
3. Glossy like toy plastic: those themes' finish was `roughness 0.45`, `clearcoat 1`, `clearcoatRoughness 0.15`. Felt's is matte fabric ([Reference images](#reference-images) rule 3), and a figure takes the theme's finish, so this too needs the user's word.
4. Use low domed knobs (a cylinder with a flattened half sphere, scaled to 0.3 in height) and little round feet.
5. No face or other decoration unless asked (see [Building shapes](#building-shapes)). A face (eyes, cheeks, smile) was tried on the left panel and removed.
6. If a word in the request is unclear (for example "bumble": bubbly or bumblebee?), pick one reading, say which one you picked, and make the other one easy to switch to (such as a colour option).

## Checking the result

1. Type-check after every change: `npm run typecheck` in `typescripts/animation`. It checks the page (`tsconfig.json`) and the dev-server code (`tsconfig.node.json`: `vite.config.ts`, `osc-bridge.ts` and `stream-bridge.ts`).
2. Look at it, don't only compile it. Start a test server on a spare port and take a screenshot with headless Edge:

   ```powershell
   $p = Start-Process node -ArgumentList 'node_modules/vite/bin/vite.js','--port','8099','--strictPort','--host','127.0.0.1' -PassThru -WindowStyle Hidden
   & "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless --use-angle=swiftshader --enable-unsafe-swiftshader --virtual-time-budget=5000 --window-size=1000,700 --screenshot="shot.png" http://127.0.0.1:8099/
   Stop-Process -Id $p.Id -Force
   ```

   Wait until the server answers before taking the screenshot. Start Vite with `node`, because `npx` can't be started from `Start-Process`. Never use port 8087 for tests, since that is the user's dev server. Other sessions may be testing at the same time, so if 8099 is taken, use another spare port. Stop the test server by its PID.
3. To look at a small figure up close, change its preview's `camera` in `src/previews.ts` only for the screenshot, and restore the file afterwards.
4. Three.js r186: `PCFSoftShadowMap` is deprecated, so use `PCFShadowMap`. `THREE.Timer` is in the core, so use `timer.update(time)`, `getDelta()` and `getElapsed()`. While the page is still busy loading, the first frame's `time` can be earlier than the timer's start, which gives a negative delta. The stage clamps it at 0, because a negative elapsed time crashed the MIDI keyboard demo.
5. The preview fits the sun's shadow to the previewed figure (`Stage.fitShadow()` in `src/Stage.ts`, called whenever a figure is shown): the shadow camera covers the figure's footprint and the shadow a tall part throws (about 0.65 × its height), at least ±0.52 m, and the sun sits far enough out to be above the figure's top. Too-large bounds make small figures' shadows blurry. Too-small bounds, or a sun below a mast's top, cut shadows off.
6. The shadow's offsets grow with those bounds (`bias -0.0005`, `normalBias = 0.01 × reach`), because each shadow texel covers more of a big figure. Without them, large or thin surfaces (a sail, a hull) show stripes of shadow acne.
7. **Screenshots of a moment in motion**, such as a leap that lasts 1.4 s, need exact frames. Drive headless Edge through its remote-debugging protocol, and before the page loads (`Page.addScriptToEvaluateOnNewDocument`) wrap `requestAnimationFrame`, so that every frame hands the stage a clock that moves exactly 1/60 s and stops at a chosen frame. The stage then keeps drawing that frame (with a delta of 0) until the clock moves on. Find the frames in a numeric run of the same preview in Node. With software rendering the Kuwahara filter makes each frame take seconds, so play the frames with `?kuwahara=0` and turn the filter on only for the paused frame, through the page's own settings module: `import('/src/settings.ts').then((s) => s.setKuwahara({ on: true, radius: 5 }))`. Look at a larger window too (1600×1000): a detail that vanishes at 1000×700 may read at a typical size. **Start that clock from the page's own time** at its first frame, not from a fixed number: the stage's timer starts on the page's clock, and a clock handed in from a fixed 1000 ms gave it a first delta of 0.73 s, so every frame was 0.73 s later than planned and the firefly's flash shots came out between flashes. Read the figure's own clock back (through the stage, below) before trusting a timed shot. **Check what draws before trusting a frame rate:** a reused browser profile once gave SwiftShader no WebGL, and the page, drawing nothing, ran at 60 frames a second instead of 0.5. Print the renderer's name with each measurement (`WEBGL_debug_renderer_info`). **A test page can reach the stage without a code change:** the animation loop calls `this.frame()` through the prototype, so patching `Stage.prototype.frame` from `import('/src/Stage.ts')` catches the instance, with its camera, orbit controls and preview. Setting `controls.target` and `camera.position` there puts the camera anywhere for a close-up, without touching `previews.ts` (rule 3), which other sessions may be changing.
8. **Numeric checks run the real modules in Node** through Vite's `createServer({ root, configFile: false, appType: 'custom', server: { middlewareMode: true } }).ssrLoadModule(...)`; `vite-node` is not installed. `configFile: false` keeps the OSC bridge from starting, and a test server started from `vite.config.ts` needs its own `OSC_PORT`, since the user's dev server holds 57121.
