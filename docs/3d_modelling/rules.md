# 3D Modelling Rules

Rules for building 3D figures with Three.js in `typescripts/animation`. They come from building the grand piano (`src/figures/Piano.ts`) and the MIDI keyboard (`src/figures/MidiPiano.ts`). Follow them for every new figure.

## Project

1. The project is Vite + TypeScript + `three`, plus React, zustand and shadcn/ui (on Tailwind CSS) for the control panel only (see [Control panel](#control-panel)). The dev server runs on port **8087** (`npm run dev`).
2. One figure per file in `src/figures/`. The file is named exactly like its class, in PascalCase: `MidiPiano.ts` exports `class MidiPiano extends THREE.Group`. On Windows, rename a file's case in two steps (`midiPiano.ts` → a temporary name → `MidiPiano.ts`), because the file system ignores case.
3. **Every figure has a spec** in a markdown file with the same name next to it: `MidiPiano.ts` has `MidiPiano.md`. See [Figure specs](#figure-specs).
4. **A figure with distinct body parts gets its own folder**, named like the figure. Example: `src/figures/Penguin/`, which holds:
   - `Penguin.ts`, which puts the parts together and decides where each part's pivot sits on the figure
   - `Penguin.md`, the spec
   - one file per part, named like its class in PascalCase: `Head.ts`, `Body.ts`, `Wing.ts`, `Foot.ts`, `Tail.ts`
   - `parts.ts` (lowercase, since it isn't a class) for what the parts share: the materials built from the theme, and helpers such as `mesh()` and `ellipsoid()`

   Each part is a `THREE.Group` whose origin is its pivot (the neck, shoulder, heel or tail base). It takes the shared materials, plus `side: -1 | 1` when it comes in a left and right pair. The part owns its shape and its resting pose. The figure owns where the part is placed, and exposes each part as a `readonly` field (`penguin.head`, `penguin.leftWing`) for animation.
5. **Resting poses go in an inner group** inside the part (a wing's outward tilt, a foot's outward turn, a foot's scale), so that the part's own rotation is 0 at rest and animation only has to add movement.
6. The preview shows one figure at a time. Each figure has an entry in the `previews` table in `src/previews.ts` (the figure, camera position and target, and its demo animation), and the tree on the panel's Figures tab or `?figure=<name>` picks one. The default, `defaultFigure`, is the figure being worked on. Figures are never deleted when they stop being the default. A demo that plays several behaviours in turn is a list of steps, each a start action and a done test (a time, or a state such as "back at the start" or "stopped"), because some behaviours last as long as the figure makes them.
7. Everything is built in code from primitives. No imported model files (`.glb`, `.obj`).

## Control panel

The preview has a control panel in the top right, and it will grow a lot. It has vertical tabs on its right edge, by the screen's edge, as the user asked:
- **Figures**: a searchable tree of the figures by folder
- **Behaviours**: the shown figure's behaviours
- **Story**
- **Environments**
- **Settings**: the camera's direction, the theme and Kuwahara
- **Stream**: live streaming the scene to YouTube over RTMP, drawn on the page or by the dev server

The panel is React; the scene is plain Three.js.

1. **Settings flow one way.** `src/settings.ts` holds every setting in one store (zustand). The React components in `src/panel/` read settings with `useSettings` and change them only through the setters in `settings.ts`. `apply()` in `src/main.tsx` passes every change to `src/Stage.ts`, which owns the renderer, camera, lights, effects and animation loop and shows the figure in its environment. React never touches the scene and never runs per frame. The one way back: dragging the view away from the picked camera direction sets that setting to free (the stage's `onDirectionLost`, wired in `main.tsx`; see rule 9).
2. **Stage setters do nothing when the value is unchanged** (`show(preview, environment, theme)`, `setCameraDirection(direction)`, `setKuwahara(radius)`), so `apply()` can hand over all the settings on every change.
3. **Every setting is kept in the URL** under its own name (`?story=`, `?figure=`, `?environment=`, `?theme=`, `?kuwahara=`, `?camera=`), so a reload keeps it. Only settings that change are written, so a figure you never picked keeps following `defaultFigure`, and until you pick an environment each figure shows in its own.
4. **A new figure, environment or theme rebuilds the figure and its environment**, and restarts the demo. Both build their materials from the theme, and a preview is built for its environment. A new figure also moves the camera to its preview's view; a new environment or theme keeps the view. The old geometries and materials are freed, including the `props` a demo uses outside the figure (the keyboard the penguin only holds now and then).
5. **To add a control:** add the setting to `Settings` in `settings.ts`, with its default, how it is read from the URL (`fromUrl`) and written back (`toParam`), and a setter. Give `Stage` a setter that does nothing when the value is unchanged, and call it in `apply()`. Then add the control to the tab it belongs to in `src/panel/Panel.tsx`, built from the blocks in `controls.tsx` (`Toggle`, `Slider`, `Select`, `RadioList`; see [rule 8](#control-panel)). A kind of setting that fits no tab gets a new entry in `TABS`.
6. **Check controls in a real browser session**, not only a screenshot. Drive headless Edge through its remote-debugging protocol from a small Node script: load the page, click, move the slider with the arrow keys, pick menu options, then read back the controls and the URL, and fail on any console exception. After each page load, wait for the panel to appear instead of sleeping a fixed time: with software rendering and a large Kuwahara radius it took up to 8 s. The controls are Base UI, not native inputs: the switch is `[role=switch]` with `aria-checked`, and the slider's thumb holds an `input[type=range]` that takes the arrow keys. A menu opens on a press of its trigger (`[data-slot=select-trigger]`). Pick options only inside the open popup (`[data-slot=select-content][data-open] [role=option]`): a menu that has been opened keeps its hidden popup in the page, and the penguin's Hold menu also lists `midi-piano`. The popup puts the picked option over the trigger, so in a long list (the figures) other options can be scrolled out of view or sit under the scroll arrows; scroll the option to the middle before clicking it. Read a menu's value from `[data-slot=select-value]`, because the trigger's text also holds a hidden ▼ from its icon. Open a tab by clicking its `[role=tab]`. Find the shown panel with `checkVisibility()`, not `:not([hidden])`: Base UI un-hides a closing panel only after its exit animation, and the panel hides it at once with `inert:hidden`. The figure tree's rows are `[role=treeitem]`, with the name in `.truncate`, `aria-expanded` on folders and `aria-selected` on the picked figure; the search box is `input[aria-label="Search figures"]`. Story and environments are `<label>` rows in `[role=radiogroup][aria-label=Story]` (or `Environment`), each holding a `[role=radio]` with `aria-checked`.
7. **Behaviour buttons.** The panel's Behaviours tab offers the shown figure's behaviours, named exactly as its spec writes them, one button each beside an input for each argument (a menu when the preview lists `options`, such as the fish's directions; otherwise a text field, where Enter runs it). Each preview lists them in `behaviours` in `src/previews.ts` with its arguments' defaults, and the stage hands them to the store in `src/behaviours.ts` when it shows the preview. They are actions, not settings, so they are not kept in the URL, and they are the one place the panel reaches the scene: a click runs the behaviour on the figure. The first one run stops the demo (wrap each runner with `demoStopper`), so the figure does only what it is told; the penguin also stops walking and puts down what it holds. **Restart demo** builds the preview again (`stage.restart()`, keeping the view). A value the figure can't read (an unknown chord) shows its error under the row. **When a spec gains a behaviour, add it to its preview's list.** For a figure whose spec has none (the boat, the rod, the trees), the tab says so.
8. **The panel is built with shadcn/ui**: Base UI underneath (`@base-ui/react`, preset `base-nova`), styled with Tailwind CSS v4 (`@tailwindcss/vite`). The components are copied into `src/panel/ui/`, because `components.json` points shadcn's aliases into `src/panel/`. To add one, run `npx shadcn@latest add <name>` in `typescripts/animation`. Style components with `className` in the blocks rather than by editing `ui/`, so that `add <name> --diff` shows only upstream changes. `src/panel/panel.css` holds Tailwind and the theme's colour variables; everything else is Tailwind classes. `@/` means `src/` (tsconfig `paths`, which Vite reads through `resolve.tsconfigPaths`). The blocks in `controls.tsx` wrap the components:
   - `Toggle`: a switch; clicking its label flips it too
   - `Slider`: a slider with its value in the third column. The shadcn slider draws one thumb per value, so its value goes in as a one-element list.
   - `Select`: a menu, labelled with Base UI's own `Select.Label`
   - `Action`: a button
   - `Field`: a text field
   - `Choice`: a menu with no label of its own
   - `RadioList`: a few options, one row each; clicking a row picks it, and an option's `hint` shows after it, such as the Environments tab's "figure's own"
   - `SearchTree` (in its own file): a document tree with a search box. The search keeps the leaves whose folder and name hold the text, and Enter in the box picks the first match. In the tree, the arrow keys move and open or close folders, Enter picks, and typing goes on in the search box.

   The Figures tab's tree comes from `figureTree.ts`. It places each figure by the path of its spec: `animals/Bear.md` goes under Animals, and a folder named like its figure (`Penguin/Penguin.md`, a folder of parts) sits beside the other figures rather than being a folder. So a figure goes in its folder once it has its spec, and until then it shows at the top (cliff, cloud and fog so far). Folders come first, then figures in the `previews` table's order. The tree takes the panel's height and scrolls under the search box, which stays in view.

   The Settings tab and the behaviours share three columns (label, control, value) through `grid-cols-subgrid`. The panel is a fixed 24 rem wide rather than sized by its content: a menu is as wide as the option it shows, so the panel would jump with every pick. The card is opaque, because over a dark scene a see-through card turned grey and hid the controls' light borders.

   The tabs stay mounted while hidden, so typed values and a search survive a switch. The open tab is kept in `localStorage`, so it survives the reloads a code change brings; it isn't a setting of the scene, so it is not in the URL. `ui/tabs.tsx` is the one generated file edited: it now passes `orientation` on to Base UI. The generated file dropped it, so vertical tabs had horizontal arrow keys and `aria-orientation`.
9. **The camera's direction** (the user's "CameraDirection control": the Settings tab's Camera menu, `?camera=`, `src/camera.ts`) says which way the camera looks at the figure.
   - **The choices:** the figure's own view (its preview's camera, the default), eight directions round it named from the figure's side (it faces +z and its left is -x, so `left` shows its left flank), and `top`, straight down with its front toward the bottom of the screen.
   - **Where it puts the camera:** a direction keeps the preview's target and distance and, round the sides, the height the preview looks from (kept between 7° and 60° above level), so a figure is framed as its preview frames it.
   - **Moving there:** picking one glides the camera round the target, the short way, over about half a second (`Stage.glide`, exponential easing like every setter). The orbit controls' damping is off during the glide, so the tail of a drag can't fight it. Taking hold of the view stops a glide.
   - **Free after a drag:** once a drag turns or tips the view more than half a degree from the picked direction, the stage reports it and the menu says `free (dragged)`, so picking the same direction again moves the camera back; zooming and panning keep the direction. `free` leaves no URL parameter, since a dragged view can't be written down.
   - **A new figure** shows from the picked direction (the stage gets the direction before `show()`, so it appears from it at once, without a glide); from `free` it goes to the figure's own view, and the menu says so. A new environment or theme keeps the view, as before.
   - **Checked** in a browser session through the remote-debugging protocol: picking directions, dragging, picking again, loading `?camera=right`, changing the figure from a direction and from free, and a bad `?camera=`, reading the menu and the URL each time and comparing screenshots.
10. **The Stream tab** streams the scene live to YouTube, as the user asked ("connect youtube streamurl with rtmp"). YouTube Studio shows the stream URL (`rtmp://a.rtmp.youtube.com/live2`, filled in) and the stream key to paste; the tab also takes a quality, 720p or 1080p at 30 fps, and has Go live and Stop. Above them are **Render** and **GPU**, as the user asked ("option to render only web + stream, or stream only, or web only"; "any configuration can use gpu or not?").
    - **How:** browsers can't speak RTMP, so a page records the stage's canvas (`canvas.captureStream`, then `MediaRecorder`, WebM with H.264 where the browser can, otherwise VP8) and posts the recording to the dev server in quarter-second pieces, one after another so they arrive in order (`src/stream.ts`); it names the recording first (`/recording`), and each piece carries its id. `stream-bridge.ts`, a Vite plugin like the OSC bridge, pipes them into one ffmpeg. ffmpeg scales the picture to fit 1280×720 or 1920×1080 (bars where the drawing's shape differs), makes it a steady 30 fps H.264 (3 or 6 Mbit/s) with a keyframe every 2 s, adds a silent stereo AAC track (YouTube wants audio), and pushes FLV to the URL and key. It is plain HTTP (`/__stream/…`), so it works through ngrok or a VS Code tunnel too. Only the scene is streamed, not the panel, and only under `npm run dev`. ffmpeg must be installed (it is, through winget) or `FFMPEG_PATH` set.
    - **Render** says where the scene is drawn. It is kept in `localStorage` and locked while live.
        - **web + stream** (the default): on the page, and the page's drawing is what streams, exactly as seen (a dragged view, a pressed piano key). A hidden tab stops drawing, so the stream freezes on its last frame: keep the tab shown.
        - **stream only**: not on the page (the stage stops its loop and hides the canvas; figures are still built, for the behaviour buttons). The bridge starts a hidden (headless) Chrome or Edge with a temporary profile of its own, which opens the page as the stream's renderer: `?renderer=1280x720` and the panel's settings (`src/streamRenderer.ts`), with no panel, drawn at exactly the stream's size (no bars), recording itself. The panel steers it: each settings change, behaviour run and Restart demo goes to `/follow`, which the bridge passes on as the Vite event `stream:follow`. It streams until Stop, whether or not the panel's page stays open; a page opened meanwhile finds it, switches to stream only and takes on its settings. In place of the scene the page shows a picture of the stream, which the hidden browser sends every second (`/preview`). A code change reloads the hidden page like any other: a new recording can't continue the old one, so the bridge starts ffmpeg again and YouTube sees the stream reconnect. Errors in the hidden page go to the terminal (`/log`). The hidden browser is Chrome, Edge or Chromium where they install, or `STREAM_BROWSER`; `STREAM_BROWSER_ARGS` adds flags.
        - **web only**: on the page, and nothing streams: the stream fields and Go live are off.
    - **GPU** (on by default, kept in `localStorage`): ffmpeg encodes on the graphics card with the first of its encoders that works on this machine, each tried once on a second of test picture (NVENC, Quick Sync, AMF, VideoToolbox, Media Foundation, Vulkan, VA-API: those this ffmpeg has); the terminal says why the others don't. With stream only, the hidden browser draws on the graphics card too. Off: x264 on the CPU, and SwiftShader for the drawing (`--disable-gpu --use-angle=swiftshader`). A page's own drawing (web + stream) is its browser's choice. On this machine (RTX 3050, driver 572.83) ffmpeg 9's NVENC needs driver 610 or newer, so Media Foundation's NVIDIA encoder is used; a hardware encoder takes about a quarter of x264's CPU time at 1080p. Without the graphics card the fox scene draws at about 12 pictures a second instead of 30.
    - **An action, not a setting,** like the behaviours: nothing of it is in the URL. The key is a secret: it is never stored (a password field, typed again after a reload), and the bridge masks it (`••••`) in the terminal and in every message. The stream URL, Render and GPU are remembered, in `localStorage`. The bridge takes only `rtmp://` or `rtmps://` URLs, because ffmpeg writes to a file when given a path; the key must be letters, digits, `-` and `_`.
    - **Status:** the page asks the bridge once a second: connecting, then live with the time, the new pictures a second (ffmpeg's frames less those it sent twice to keep 30, from `-progress`) and the bitrate, and a line saying what draws the pictures (the recording page's WebGL renderer) and what encodes them; or what ffmpeg said when it gave up (YouTube refusing the key, the network down), which also stops the recording. ffmpeg runs with `-loglevel error`, because a live recording's timestamps make routine warnings that would flood the terminal; the cut-off recording at a stop is not reported.
    - **When the page goes:** with web + stream, a closed or reloaded page ends the stream at once (`sendBeacon` to `/stop` on `pagehide`), and the bridge ends it by itself after 15 s without a piece (40 s for the hidden browser, which also has to start and to reload). On Windows the hidden browser also closes when the dev server's process ends, however it ends: Node keeps its children in a job that closes with it.
    - **Checked without YouTube:** ffmpeg can be the RTMP server too (`ffmpeg -listen 1 -f flv -i rtmp://127.0.0.1:19350/live2/<key> -c copy received.flv`), started again after each connection so that a reconnect is caught. The test ran its own dev server (port 8123) with `STREAM_BROWSER_ARGS=--remote-debugging-port=…`, and drove headless Edge through the remote-debugging protocol: each Render mode; stream only with the GPU on and off; that the hidden page draws at 1280×720 with the panel's settings, follows a theme and a behaviour (seen in its websocket frames), reconnects after a reload, streams on while the panel's page is closed, is found again by a new page, and closes at Stop; the drawing-and-encoding line; and what the listener received (H.264 1280×720 at 30 fps, with AAC). Type into the fields with `Input.insertText` after clicking them; setting `value` directly doesn't reach React. A menu's shown value is in its `[data-slot=select-value]`.

## Figure specs

1. The spec (`<Figure>.md`, next to `<Figure>.ts`) belongs to the user. It says what the figure is and how it behaves. The code follows the spec, not the other way round.
2. Before changing a figure, read its spec. When the spec changes, bring the code in line with it.
3. Don't rewrite or reformat the user's spec text. If a spec is missing, write a short draft from the existing code, say at its top that it is a draft for the user to correct, and use the same layout as the other specs.
4. Implement API names exactly as the spec writes them, even when they break the usual TypeScript style. `MidiPiano.md` asks for `PlayChord(chord string)`, so the method is `PlayChord`, not `playChord`. Point to the spec in a comment next to such a method.
5. Where the spec is silent, choose a sensible behaviour, write it in the code comment, and tell the user so they can put it in the spec. For example, `PlayChord("A")` presses A major with the root in the C4 octave and releases the previous chord.
6. Layout of a spec, as the user wrote it:

   ```markdown
   # <Name> Figure.

   ## Animation Behavior.
   1. `MethodName(arg type)`

       Example:
       `figure.MethodName("value")`
   ```

## Reference images

1. When the user gives a reference image, match its **shape and proportions** part by part: list the differences first (head size, face, beak, body shape, wings, material), then fix them, then compare a screenshot with the reference again.
2. Match its **colours through a theme**, never by hardcoding them in the figure. Add a theme for the reference's palette and finish (the penguin reference became the `felt` theme: black, off-white, orange, matte fabric). `felt` is now the default theme for every figure (`defaultTheme` in `theme.ts`); the panel's Theme menu or `?theme=` switches to another, such as the brand.
3. For a soft material (felt, plush), use the theme `finish` with `roughness 1`, no clearcoat, and a low `sheen` (about 0.3). A strong sheen turns black into grey and orange into salmon.
4. Parts that are shiny on any material, such as eyes, use `gloss(color)` from `theme.ts` rather than the theme's finish.
5. To shape organic parts, `ellipsoid()` in `Penguin/parts.ts` takes a `taper` (`{ top, bottom }`) that narrows one end: a pear-shaped body, a wing narrowing to its tip.

## Effects

1. Post-processing effects live in `src/effects/`, one file per effect (lowercase, since they export a shader factory rather than a class), and run through three's `EffectComposer` in `src/Stage.ts`: `RenderPass` → the effect as a `ShaderPass` → `OutputPass`. `OutputPass` does the sRGB conversion that the renderer would otherwise do, so colours stay the same as without effects.
2. Render into a multisampled target (`samples: 4`, `HalfFloatType`), because a composer's targets have no antialiasing by default.
3. **Kuwahara** (`effects/kuwahara.ts`) gives a painterly look: flat patches of colour with sharp edges. It is on by default at a 5 px radius. The control panel's Settings tab has a **Kuwahara on/off switch** and a **Radius slider** (1–12 px, greyed out while the filter is off). Both keep `?kuwahara=<radius>` in the URL in step (`0` = off), so a reload keeps the setting. The radius is a shader uniform, so the slider changes it live without recompiling. It is set in CSS pixels and multiplied by the pixel ratio, capped at 24 device pixels.
4. The Kuwahara switch and slider are panel controls like any other. See [Control panel](#control-panel) for how they are built and checked.
5. Keep the Kuwahara radius around 4–6 px. At 10 px the classic four-quadrant filter shows blocky square smears and smudges small details like eyes into patches.
6. Measure brand colours with the effect on and off. Measured on the brand penguin at a 5 px radius: background and belly unchanged, indigo within a few units (head `#4B43D7` → `#4C44D9`), slightly lighter on curved sides where it averages in the highlight (`#4740C9` → `#5049D5`).
7. **The overlay layer** (`src/overlay.ts`, layer 1) is drawn after the effects, on top of everything, so the Kuwahara filter never smears text: speech bubbles live there. With the filter on, an `OverlayPass` sits between the Kuwahara pass and `OutputPass`; with it off, `drawOverlay()` follows `renderer.render()`. The main camera and the raycaster see only layer 0. `drawOverlay()` takes the scene's background away while it draws: in three r186 a colour background clears the picture on every render, even with `autoClear` off, which first left only the bubble on an empty background.
8. **Keep thin details sharp.** The filter averages away anything narrower than its radius: at 5 px an 8 mm line 2.5 m away (about 2 px) all but vanished. `keepSharp(material)` in `effects/kuwahara.ts` marks a material to pass through the filter unchanged while everything around it stays painterly. The material stays opaque but is drawn without blending, so it writes its opacity (0.5) as the pixel's alpha, and the filter passes any pixel with alpha under 0.9 (its anti-aliased edges too). It is still drawn in the scene with depth, so it hides behind nearer things, unlike the overlay layer. The canvas has no alpha, so nothing else sees the mark. Use it only for details that must read (the fishing line), not to make whole figures sharp.

## Units, axes and origin

1. Units are **meters**, and figures are **real-world size** (a grand piano is 1.5 m wide, a white key is 23.5 mm).
2. `y` is up and the floor is `y = 0`. The front of the figure (where a person stands) faces **+z**. Width runs along **x**, left is −x.
3. The origin is the **bottom center**, on the floor. If the figure has feet, the origin is under the feet. **A handheld figure** that never stands on its own (the fishing rod) has its origin where the hand holds it instead (the pole's axis 30 cm from its butt): that is the pivot it swings around, and where `Hold()` puts it.
4. The header comment of each figure file states what it is, the units, the axes and where the origin is.

## Building shapes

1. Put every dimension in a named constant at the top of the file. Derive dependent sizes from them (for example `BODY_WIDTH = LEFT_PANEL + WHITE_COUNT * WHITE_WIDTH + RIGHT_PANEL`), so that changing one number keeps the parts aligned.
2. Use small helpers: `mesh()` creates a mesh and turns on `castShadow` and `receiveShadow`, and `box()` places a box by its bottom instead of its center.
3. Straight parts: `BoxGeometry`. Rounded parts: `RoundedBoxGeometry` from `three/addons/geometries/RoundedBoxGeometry.js`, with a radius smaller than half of its smallest side. Curved outlines (such as a grand piano case): a `THREE.Shape` drawn from above, then `ExtrudeGeometry` rotated so that it extrudes upward.
4. Repeated parts (keys, legs, pedals) share one geometry and one material. A part gets its own material only when it changes on its own (a pad that lights up, a knob with its own colour).
5. Build all materials in one `createMaterials(theme)` function, which takes every colour from the theme (see [Colour and theme](#colour-and-theme)). To change a colour, change or add a theme, not the figure.
6. A figure that has lots of empty space on one side (such as the left panel of a keyboard) keeps it on purpose, as room for controls added later. Don't fill it or shrink it without being asked.
7. **No decorations the user didn't ask for.** Build the object itself, not extras on it. The user removed both extras added so far: a face on the MIDI keyboard's left panel and a flag (pennant) on the boat's mast. **The user's word for a part may not be ours:** after the pennant was gone, "the boat still has a flag" meant the sail (a triangle on a pole reads as a flag), so the sail and its boom were removed too. Then "remove the pool in the boat" was a typo for pole: the bare mast went as well, and the boat is a hull with a rudder. When the user says a part is still there after it was removed, don't just repeat that it's gone. Check what they see (fetch the module from their dev server on 8087 via `localhost`, which listens on IPv6 only, and take a screenshot), then find the part that matches their word.
8. **Smooth, curved hulls and shells** (a boat hull) are built from a shape function of two numbers, `u` along the length and `t` around a cross-section, turned into a surface by `gridGeometry(rows, columns, point)` in `Boat/parts.ts`. Wind the grid so the triangles' front faces point out (see `Hull.ts`), and close an open end with a `Shape` of that end's cross-section (the transom). A closed body (a fish) uses `tubeGeometry` in `Fish/parts.ts` instead, whose last column joins the first so the surface has no seam, and whose sections shrink to a point at both ends. Thin fins are a `Shape` drawn from the side and extruded a few millimeters (`finGeometry`).
9. **A thin shell has two sides.** Draw the outside with a front-side material and the inside with the same geometry and a `BackSide` material in another colour. Only the outside mesh casts shadows; if both do, each side shadows the other and the surfaces fill with fine stripes (shadow acne).
10. **Parts inside a curved shell** (a bench across a hull) are sized from the shell's tightest point where they touch, not their center: the hull narrows downward and toward both ends, so a bench as wide as the hull at its center pokes its corners out through the sides. Check with a raycast from each corner toward the shell. A `Raycaster` only hits the side of a surface its material draws, so cast against the inside mesh when the ray starts inside.
11. **Lines and cords** (fishing line) are drawn far thicker than real: the rod's line is an 8 mm cord, after the user asked twice for a thicker rope. They cast no shadow, and they are kept out of the Kuwahara filter with `keepSharp()` (see [Effects](#effects)), since the filter averages away anything a few pixels wide; that, more than the thickness, was why the rope kept looking thin. The fishing rod's line is tied just below the tip, where a band of wound line (the lashing) sits on the pole, and hangs from there. A hanging line is its own group at the point it hangs from, turned in `update()` so it points straight down in the world whatever way the figure is held.
12. **Textures are made in code**, like the shapes: no image files. `src/textures/woodGrain.ts` draws a wood-grain tile (planks 12.5 cm wide with seams, a butt joint in each, wavy growth rings and streaks) into a `DataTexture`, made once and shared. It is grey, so the material's theme colour shows through: `wood(theme)` in `theme.ts` is the theme's `wood` colour in its finish with that texture (the boat's planks, bench, rudder and tiller). One tile is 1 m, so give a textured surface **texture coordinates in meters, with u along the grain**: `gridGeometry`'s `uv` callback for a hull (u along the hull, v around it sized to the widest section, so the planks narrow toward the ends like real strakes), `grainUVs()` in `Boat/parts.ts` for boards, blades and rods (grain along the longest side), and a `ShapeGeometry`'s own coordinates, which are already in meters (the transom). The Kuwahara filter softens the grain but keeps the planks. **Bark** (`src/textures/bark.ts`) is the same idea for branches: ridges along the branch split by darker furrows, darker than the grain, so `bark(theme)` in `theme.ts` turns the theme's wood colour into bark and a cut end in the plain wood colour shows paler, like fresh wood. Its tile is 20 cm and tiles both ways, so give a branch texture coordinates in meters along it and exactly one tile round it: the bark wraps without a seam. Both textures share the tileable noise in `src/textures/noise.ts`.
13. **Traditional, not modern.** The user found a spinning rod (reel, guides, foam grips) too modern and asked for one made from a tree branch (*ranting kayu*): a crooked, tapering pole with bark, cut ends and twig stubs, the line tied at the tip. At the user's request it is a stout branch (5.2 cm across at the butt, 1.8 cm at the tip) with small details that make it real: a side twig snapped and hanging from its splintered break, and a leafy twig and a leaf near the tip (leaves use the theme's `grass` colour, its foliage colour). The boat went the same way: its sail and mast came off and it became plain wood. For an everyday object, build the simple, traditional version (natural materials, hand-made, as it would be found in an Indonesian village) unless the user asks for modern equipment.

## Moving parts

1. Every moving part sits in its own `Group` whose origin is the **real pivot**: the back edge of a key, the hinge of a lid, the center of a knob. Then its rotation matches the real movement (for example, `rotation.x > 0` dips the front of a key).
2. Anything that turns around its own axis (a knob or a wheel) gets a visible marker (a white line or dot). Without one you can't see it turn.
3. The public API uses real-world terms: `setKeyPressed(midi, pressed)`, `setKnob(index, 0..1)`, `setPitchBend(-1..1)`. Clamp values to their range, and ignore out-of-range indexes and notes instead of throwing an error.
4. Setters only set a **target**. `update(delta)` moves each part toward its target with `t = 1 - Math.exp(-speed * delta)`, so the speed is the same at any frame rate. The caller calls `update(delta)` once per frame.
5. Ranges and counts are static fields (`LOWEST`, `HIGHEST`, `KNOB_COUNT`), so demos and other code read them from the figure instead of hardcoding them.
6. **One-shot and continuous behaviours.** One-shots (`Flap()`, `Jump()`) play once and end by themselves. Continuous ones (`Walk()`, `Run()`) keep going until another behaviour replaces them, so they need a way to end: the penguin has `Stop()`, added beyond its spec and reported to the user. Ease between states (standing, walking, running) with the same exponential easing as setters, so switching never snaps.
7. **A figure that walks moves itself.** It goes forward along its own +z at a speed that matches its steps, and exposes that speed (`penguin.speed`, in m/s). Callers steer by turning it (`rotation.y`); turning by `speed / radius` radians a second walks a circle of that radius at any gait. Jumps and other in-place moves stay inside the figure and never change its position.
8. **No sliding feet.** A planted foot must stay put on the floor. When each foot is planted for half a cycle and slides back one stride under the body, the forward speed is `2 × stride × cadence`. Check it numerically, not by eye: run `update()` in small steps with `vite-node` and confirm a planted heel's world position doesn't move over a whole stance while the body does.
9. **Split a walking figure into a rig and a torso.** The rig (everything) takes the jump height and squash. The torso (everything above the feet) leans, bobs, rolls over the planted foot and twists, while the feet step on the floor beside it. The head can undo part of the torso's lean and roll so it keeps looking ahead.
10. **A figure that swims moves itself in three dimensions.** The fish's `SwimOnSurface(direction)` and `SwimOnDepth(direction)` turn it toward the direction the short way round, send it forward along its own +z at `speed`, and raise or lower it to its depth, nose up or down. It takes the water's surface to be `y = 0` of its parent, as in the lake, and exposes its two heights (`fish.surfaceY`, `fish.depthY`). A `Direction` is in the scene's axes: `forward` +z, `back` −z, `left` −x, `right` +x; an unknown one is ignored.
11. **Swimming motion follows the speed.** A fish moves about 0.75 of its length per tail beat, so the beat quickens and widens with speed and slows to a gentle idle while it hovers. The body sways against the tail, the pectoral fins paddle, and in a turn the fish leans in and bends its tail toward the turn. Pitch, lean and sway happen in an inner rig pivoted at the middle of the body, so the fish turns around its middle rather than its origin on the floor. Check a swim loop numerically (positions over time) as well as by eye: the fish demo's square stays in place loop after loop because each side ends where the fish crosses the square's edge. Timed sides kept it in place only until a leap carried the fish faster than it swims.
12. **A leap is planned, not steered.** `JumpOutFromWater(height)` works out the whole leap when it starts, so the fish clears the water by exactly `height`: at the top its lowest point is that far above the surface, which is `position.y = height`, since the origin is under the lowest point. The fish's middle leaves the water at 60° with just the up speed gravity needs, `√(2g × rise)`. Near the surface it first dives until its middle is 35 cm down, to gather speed. Its up speed then grows with the square of the time (a cubic), so its nose turns up without a jolt. In the air it has nothing to push on, so it turns at a steady rate from nose up to as far nose down, level at the top. Unlike the penguin's jump, the leap moves the fish itself, since its height is part of where a fish is, and it holds its heading throughout. Swimming behaviours given in the air wait until it is back in, where drag above its swimming speeds slows it back to them. A second leap is ignored until the plunge back in has slowed. Where its middle breaks the surface, going out and coming back in, the fish sends a `splash` event with its velocity, and the preview hands it to `environment.water.splash` (see [Environments](#environments)). Check it numerically: `Box3.setFromObject(fish, true).min.y` at the top equals the height, the fish is level there, and position and speed change smoothly from frame to frame, at 240 fps and at 20.
13. **Speech bubbles** (`src/speech/SpeechBubble.ts`, shared by any figure that talks; the penguin's `Speech(text)`): a comic bubble, a sprite that always faces the camera, in the theme's `light` with its outline and words in `dark`, sized in meters (text 3.2 cm, lines up to 34 cm) and drawn on a canvas at 1.6 px a millimeter. A bubble holds at most **nine words**, as the user asked (a word over 50 characters is first cut into 50-character pieces, each counted as a word; `splitSpeech()`); in a bubble the words wrap into lines up to 34 cm wide and the bubble is as tall as its lines, so a long piece makes a tall bubble. Bubbles pop up from the tail one after another, each staying about 0.8 s plus 0.06 s a character (at least 1.4 s), and saying something new cuts off the rest. The bubble hangs outside the rig, so a jump's squash never squashes the words, and rises with the jump. The stage frees a sprite's own texture when the figure goes; other textures stay, since some are shared.

## Environments

An environment is the surroundings a figure is shown in: so far the plain `floor`, the `lake` and `grass`, with more to come. The panel's Environments tab or `?environment=<name>` picks one, and the tab marks the figure's own. Until then each figure shows in its own (`figureEnvironments` in `src/previews.ts`: the boat and the fish on the lake, the trees on the grass, the rest on the floor); a pick stays when the figure changes.

1. Environments live in `src/environtments/<Name>/` (the folder is spelled as the user created it), built like a figure, with a spec next to the code: `Floor.ts` is one plane, `Grass.ts` a lawn, and `Lake.ts` puts together `Ground.ts`, `Water.ts` and what grows and stands on them. Every colour comes from the theme: bare land is `scene.floor`, the water `scene.water`, and lawns and grass `scene.grass`.
2. **Each environment has an entry in the `environments` table** in `src/previews.ts`, and the Environments tab lists them in table order. The entry builds the `scenery` and says where a figure goes: `land`, where a figure stands, and, if there is water, `water.at`, where a figure goes whose preview has `place: 'water'`, with `water.heightAt(x, z)` measured from there. The stage moves the scenery so that the figure's spot is at the origin, so figures, cameras and shadows stay put in every environment. It calls the environment's `update(delta)` every frame before the preview's, and frees it with the figure.
3. The origin is the center, at the level figures use: for the lake, `y = 0` is the still water surface, the bed is up to 1.4 m below it and the top of the bank 0.3 m above it; the land beyond is uneven (see rule 15). `lake.surfaceAt(x, z)` and `lake.groundAt(x, z)` give the heights at a point. Anything placed on the land stands at `groundHeight(x, z)` (`Ground.ts`), never at a fixed height.
4. **Floating.** A floating figure sits its draft below the water (`Boat.DRAFT`, 0.1 m) and rides the waves: sample the water's height (`environment.water.heightAt`) ahead, astern and on both sides, then ease its height, pitch (`rotation.x`) and roll (`rotation.z`) toward them with `1 - exp(-speed × delta)`, because a hull lags the water.
5. **Keep water out of hulls.** The water is a see-through sheet at the waterline, so it runs through anything that floats, and the inside of a hull looks flooded. `keepDry(root, materials)` in `src/environtments/water.ts` marks the inside surfaces (on the boat, the hull's `inside` material; anything standing inside a hull below the waterline, such as a mast's foot, needs marking too). They are drawn after the other solid meshes and write the stencil buffer where they are the visible surface, and the water (`waterSurface(material)`) is not drawn there. Never mark the outside of a hull, or its part under the waterline looks out of the water. This needs `stencil: true` on the renderer and `stencilBuffer: true` on the composer's target (both in `Stage.ts`).
6. **Waves** are a few sine waves crossing each other, each moving at the speed deep water gives its length (`ω = √(g·k)`), 1–3 cm high on a lake. One sum moves the water's vertices, sets their normals from its slope, and answers `surfaceAt`, so a floating figure follows exactly what is drawn.
7. **The ground meets the water at a slope**, not flat, so the waterline is a crisp line instead of a band that flickers as the waves wash over it. The lakebed fades from the floor colour toward the water colour with depth, so deep water looks deeper.
8. **A preview is built for its environment.** Its entry gets it, `(theme, environment) => Preview`, so a figure can behave differently with and without water: the boat floats when `environment.water` exists and otherwise rests on its keel on the ground. A figure that only stands needs nothing.
9. **A place to stand needs room.** `land` must be flat for the figure's whole footprint, and for a walking demo's circle. The lake's is `Lake.LANDING` (defined in `Ground.ts`, since the land is shaped round it), on the +z shore 1.5 m past the top of the bank, where the uneven land is kept level for 2.2 m round it. That leaves room for a figure about 3 m across, with the water behind it (toward −z), where the preview cameras look.
10. **To add an environment:** build it in `src/environtments/<Name>/` with its spec, add its entry to `environments` with a flat `land` spot (and `water` if it has water), and check a standing figure (the penguin) and, if it has water, the boat in it, from the preview's camera.
11. **Stones on the lakeside** (`Lake/Stones.ts`): about 75 rocks in 16 clumps around the shore, from pebbles to rocks 0.7 m across (small ones far more common), some up the bank and some at the water's edge with their feet in the water, each bedded about a third into the ground so it doesn't float. Each rock is a sphere cut by random planes, drawn with flat faces; six shapes are shared, each stone turned, tilted and sized on its own. They are placed by a seeded random generator, so the lake is the same on every load, and kept 3 m clear of `Lake.LANDING`, where standing figures go. Their colour is `theme.scene.stone`. The stage's shadow covers only the figure, so distant stones cast none; the bedding keeps them looking seated.
12. **A lawn is one instanced mesh** (`Grass/Grass.ts`): 30,000 blades of one shape, each placed, turned, sized (2–4 cm, below a keyboard's keys) and shaded at random from a fixed seed, thick in the middle where a figure stands (the radius is picked evenly, not by area) and thinning out over 4 m, on ground a shade darker that runs to the horizon. A blade's two sides are both front faces with normals pointing up, so it is lit like the ground from either side; a double-sided material would light its back from below. Blades take shadows but cast none, which would add a shadow pass over all of them.
13. **Trees round the lake** (`Lake/Trees.ts`): nine trees of the [tree figures'](#trees) kinds, dealt from shuffled decks of one of each so every kind is there, each grown from its own seed and sized at random from 0.5 to 1.25 times the figure (and a little taller and slimmer or shorter and broader), on the land beyond the bank (at `groundHeight`, since it is uneven), at least 8 m apart. The user first asked for twenty, then cut it to nine as too many, and asked for the sizes to vary. None stand within 9 m of `Lake.LANDING` or on its +z side, where the preview cameras stand, so the trees frame the far shore instead of blocking the view. With them the lake built in about 0.35 s; with the sward and meadow (rule 16) it takes about 0.55 s, which every new figure or theme on the lake pays. Their crowns sway in the wind (rule 17); the wood stands still.
14. **Splashes** (`Lake/Splash.ts`, through `environment.water.splash(x, z, velocity)`): where something breaks the water's surface, drops fly under gravity until they fall back in, and two rings of ripples spread from the spot and fade over 1.6 s. Their points are set from `heightAt` every frame, 4 mm above the water, so they ride the waves. Leaving the water, 70% of the drops are dragged up after the thing at a share of its speed, so they trail behind it; coming in, all of them are thrown up in a crown. The splash grows with the speed: 50 drops at 3 m/s, a 30 cm leap. Drops are drawn far bigger than real (2–5 cm) and the rings 3–7 cm wide, because the Kuwahara filter averages away sparse small drops. Drops thrown out in a ring vanished by the top of the leap in a 1000×700 window, while dense clusters (a crown, a plume) read as painted spray. The drops are one instanced mesh and the rings a pool of eight, all in the water's colour lightened toward the theme's `light`. The rings are drawn after the see-through water (`renderOrder` 2, no depth write), or the water would cover them. The figure only says where it breaks the surface (the fish's `splash` event), and the water owns the splash, so the splash stays where it happened while the fish moves on.
15. **Uneven land round the lake** (`Lake/Ground.ts`), as the user asked: past the top of the bank the land humps and dips. Four sine waves cross it (2.7–9 m from crest to crest, together up to about ±0.3 m), and it rolls into low hills from 9 m out (up to 1 m). The humps grow from nothing over the first 1.5 m past the bank, so the bank still meets the water in a clean line, and die away round `Lake.LANDING`. The land never dips below 8 cm above the water: the water is a square sheet that runs under the land and would show in any hollow below it. The ground mesh has rings every 40 cm over the humps and 320 spokes; the old flat land's rings, meters apart, would have cut the humps into facets. Beyond the bank the ground is coloured as a lawn (`scene.grass` a shade darker, as in the grass environment), mottled in meter-wide patches that the Kuwahara filter turns into strokes of grass; the bank stays bare `scene.floor`. Check it numerically: the landing's height, the lowest land inside the water's square, and the steepest slope near the lake (16°).
16. **Grass covering the land** (`Lake/Sward.ts` and `Lake/Meadow.ts`), as the user asked ("using various types and sizes of grass"). The **sward** is 17,000 tufts of 5–8 pointed blades (three tuft shapes), 7–26 cm tall and mostly short. It is thickest near the water and round `Lake.LANDING`, and mown to 2–4.5 cm on the landing itself, below a keyboard's keys, like the grass environment. The **meadow** is 82 patches of the [grass figures](#grasses), each patch one kind (fewer Bermuda mats, chives and rosemary than the rest). Its plants are 0.45–1.6 times their kind's size, each turned, stretched and shaded on its own, leaning with the slope (a Bermuda mat lies along it). Some patches ring the landing, where the cameras look; none grow within 2.6 m of it or 1.2 m of a trunk. Each kind is grown only twice, at two details (`detail` in `GrassOptions`: 0.4 within 7 m of the landing, 0.2 and coarsened beyond), and each of its meshes is drawn as an `InstancedMesh` with one instance per plant, so the whole meadow is 28 draw calls. The first try, 80 patches spread evenly with the kinds at full detail, was 3.5 M triangles and still looked bare from eye height, since plants a few pixels tall vanish into a lawn of their own colour. What made the land read as grass was a cheap sward, thick where the cameras look, with the kinds as patches over it. Now the sward is 0.65 M triangles and the meadow 1.06 M. Neither casts shadows. The stage frees an instanced mesh's instances too (`dispose()` in `Stage.ts`).
17. **Weather now and then** (`Lake/Weather.ts`), as the user asked ("fog and wind sometimes"). Fog rolls in over about 12 s, hangs 20–35 s and clears, 40–90 s apart. Windy spells of 12–25 s come 15–40 s apart and gust while they last, with only a breath of wind between them. The first fog comes 25 s after the lake is shown and the first wind after 8 s, so both are seen without a long wait; after that the times are seeded.
    - **Fog** is the scene's `FogExp2` in the theme's background colour. An environment can give `fog` (`Environment` in `previews.ts`), and the stage puts it in the scene or clears it. At its thickest it mostly hides the far shore, 20 m off, and hardly touches a figure 2 m from the camera; but a tree figure previewed on the lake from 25 m fades out while it lasts. Speech bubbles take no fog, so their words never fade.
    - **Wind** (`src/environtments/wind.ts`) is shared uniforms (time, strength, direction), and `sway(material, wind, { sway, reach })` bends a material's meshes on the graphics card, from each mesh's or instance's origin. A point moves `sway` m at `reach` m up, growing with the square of the height, with gusts running downwind and a quicker flutter. The sward sways 7 cm at 25 cm up, the meadow 22 cm at 1 m, and the trees' crowns 35 cm at 15 m. Only the drawing moves, not shadows or `heightAt`.
    - **The water roughens in the wind** (`Water.setWind`): its waves grow up to 2.2 times as high, a 90 cm ripple runs downwind, and the glint dulls. `heightAt` uses the same waves, so a floating boat rocks more.
    - **Checking it:** a still screenshot can't show the timing, since headless Edge's virtual time hardly moves the scene's clock. To look at fog or wind, shorten the first times and the easing in `Weather.ts` for the screenshot, then restore them. Compare a windy and a calm frame with the filter off: the tall stems lean downwind.

## Trees

The tree figures live together in `src/figures/Tree/`, one file per kind next to its spec: `OakTree`, `CedarTree`, `MapleTree`, `PineTree`, `ChestnutTree`, `SpruceTree`, `ElmTree` and `WillowTree`, shown in the preview as `oak-tree` … `willow-tree`. The user's specs are empty so far (so are `BirchTree.md` and `PoplarTree.md`, which have no figure yet), so the trees have no behaviour and stand still.

1. **A family in one folder.** The kinds share their parts: `Trunk.ts` (the trunk and every branch in bark, one merged mesh), `Crown.ts` (every clump of leaves or needles, one merged mesh), `skeleton.ts` (growing the wood) and `parts.ts` (materials, the seeded random generator, limb and clump geometry). A kind's file only says its habit. Each tree exposes `tree.trunk` and `tree.crown`, with the tree's origin.
2. **Real size**, 10–21 m tall, with the origin on the ground at the foot of the trunk and the roots flaring a little below it. The tree preview (`tree()` in `previews.ts`) stands the camera back from the tree's middle by its height and width, so each tree is seen whole. Trees start on `grass`: behind a tree that size the floor's 20 m square shows its edges.
3. **Branches grow by space colonization.** Points are scattered through the crown's shape, and branches grow toward them in steps of 0.4–0.45 m, each point dropping out once a branch comes within its kill distance. A kind gives its habit: the trunk and first big limbs drawn by hand (`fan()`: an oak's low, wide limbs, an elm's vase of stems, a cedar's leaders), the crown's shape (an oak's broad, lumpy dome, a maple's egg, a chestnut's dome hollowed from below, an elm's umbrella open underneath, a willow's low dome, a pine's clouds round the top of a tall bare trunk, a cedar's flat layers), and how branches bend (`tropism`: up, or down beyond a radius, for a drooping rim). Radii follow the pipe model (a branch's r^2.5 is the sum of its children's), scaled to the trunk's radius. Without hand-drawn limbs, points all round one node pull it equally every way and it grows a single central leader, so a vase needs its stems drawn. The spruce is regular enough to build directly: whorls every 60 cm, branches shortening upward, drooping and turning up at the tips, each with a pad of needles.
4. **Leaves are clumps**: lumpy blobs (a sphere dented by a few random waves), shaded per vertex (the underside, and the bottom and inside of the crown, darker), a little past each twig tip, flattened for a pine's tufts and a cedar's shelves, stretched along a spruce's branch. The willow's curtain is cascades of tall, narrow clumps hanging from its outer branches and flaring out as they fall. Thin ribbons (like grass blades) were tried first and read as streaks under the Kuwahara filter; clumps keep the willow in the same hand as the other trees. Leaves are the theme's `grass` colour, darker for conifers (`FOLIAGE_SHADE`); bark is its `wood` colour through `bark(theme)`.
5. **Seeded.** `new OakTree({ theme, seed })`: the same seed always grows the same tree, and each kind has its own default. A loop that shrinks something each step needs a count cap besides its end test: the willow's cascades shrink by 0.9 a clump, which for some seeds converges above the hem, and without the cap it ran out of memory. Before placing trees with random seeds, build every kind with many seeds; Vite's `ssrLoadModule` builds figures in Node, without a browser.
6. **Cost.** A tree is two draw calls and 20–80 k triangles, and builds in 10–60 ms (the willow, with the most clumps, is the slowest). The clump sphere is made once and cloned.

## Grasses

The grass figures live together in `src/figures/Grass/`, one file per kind next to its spec: `CockFootGrass`, `BermudaGrass`, `TimothyGrass`, `MeadowFoxtailGrass`, `RedFescueGrass`, `ChivesGrass` and `RosemaryGrass` (chives and rosemary are herbs, but named as the user listed them), shown in the preview as `cock-foot-grass` … `rosemary-grass`. Their specs are drafts written from the code, and they have no behaviour yet.

1. **Every grass can be sized**, as the user asked: `new TimothyGrass({ theme, seed, height, width })`, in meters, each kind with its own default (`TimothyGrass.SIZE`). With only a height it keeps its shape. A plant is planned first as lines and blobs (leaf midribs, stem axes, clusters of spikelets, woody stems), and `fit()` in `parts.ts` stretches its heights and spreads to exactly that size, and its widths and radii only by the square root of the mean stretch, so a plant twice the size has leaves 1.4 times as broad, not twice. A wider plant also grows more leaves and stems (`crowd`). Blobs grow by that root and not the height, so `fit()` measures the sized plant in a few passes. Check sizes numerically: the built figure's box is within millimeters of the size asked for. Parts may share a point (a spikelet on the tip of its stem), so `fit()` scales each point once: scaled twice, a fescue asked to be 1.1 m came out 2.5 m tall.
2. **A family in one folder**, like the trees: `Leaves.ts` and `Stems.ts` (the parts, each one merged mesh; `Stems` adds a bark mesh for woody stems), `habit.ts` (tufts of leaves, flowering stems with their leaves, arching lines), `grow.ts` (plan, fit, build) and `parts.ts` (options, materials, colours, and the blade, tube and blob geometry). A kind's file only says its habit and its seed head. Each plant exposes `plant.leaves` and `plant.stems`, with the plant's origin on the ground at the middle of its foot.
3. **Leaves are ribbons** here, not clumps: blades along an arching midrib, folded into a V (keeled), each drawn front and back with its own normals leaning up, so either side is lit like the rest of the tuft. Seen from a meter or two they read as leaves, unlike the willow's ribbons seen from 30 m. Stems and seed heads are tubes (timothy's blunt cylinder, foxtail's soft spindle, Bermuda's fingers), roughened by `bumps`. Clusters and florets (cock's-foot, fescue, the chives' pom-poms) are the trees' lumpy clumps.
4. **Thin parts are drawn thicker than real**, as with the fishing line: stems 5–7 mm across, fescue's leaves 3 mm, rosemary's 5 mm. At real thickness the Kuwahara filter wiped out the stems, and the seed heads floated. Rosemary first looked like a bundle of brown sticks: thinner stems and denser, longer leaves made it a green bush.
5. **One material, coloured per vertex**: white in the theme's finish, times vertex colours taken from the theme (`palette()`). Leaves are `grass`, darker at their feet; seed heads ripen toward `wood` (straw), some with a touch of `flower`, as real ones are tinged purple; fescue's feet go toward `wood` (its red sheaths), and rosemary's undersides toward `light`. The chives' flowers are `flower`. Rosemary's stems are bark through `bark(theme)`.
6. **They start on the floor**, not the lawn, where their green disappears into the lawn's. The preview (`plant()` in `previews.ts`) takes in the whole plant, a little from above.
7. **Cost.** A plant is two draw calls and 10–85 k triangles, the most for Bermuda's mat and rosemary's needles, and builds in 5–100 ms. Blobs under 2 cm (spikelets, florets) use an 80-face sphere, not 320 (`clumpGeometry` in `Tree/parts.ts` takes a detail).
8. **Detail for plants seen from afar.** `detail` in `GrassOptions` (1 by default) is the share of leaves, stems and runners a plant grows. Under 1 the plant is also coarsened (`coarsen()` in `parts.ts`): blades keep every other point, and tubes get rings twice as far apart and fewer sides. At 0.2, timothy falls from 13.6 k triangles to 1.1 k and Bermuda from 62 k to 6.5 k. The lake's meadow uses it (see [Environments](#environments) rule 16).

## Animals

The animal figures live together in `src/figures/animals/` (lowercase, as the user named it), one file per animal next to its spec: `Cat`, `Wolf`, `Deer`, `Bird`, `Bear`, `Fox` and `Snake`, shown in the preview as `cat` … `snake`. The user gave them all the penguin's behaviours without `Flap()`. Each spec is the user's list as written, numbered 2 to 6.

1. **Shared behaviours** (`Animal.ts`): `Jump()`, `Hold(figure)`, `Walk()`, `Run()` and `Speech(text)`, plus `Stop()` (not in the spec, as with the penguin). Each animal builds its body into `rig` and poses it every frame in `pose(motion)`, from what `Animal` works out: where it is in its stride, how far into a jump, how much it holds something. A gait is a stride, a cadence and a duty (the share of a stride a foot is down), so the speed is `stride × cadence / duty`. A jump lasts the time in the air gravity gives its height, between crouches.
2. **The four-legged ones share a rig** (`Quadruped.ts`, built from a `Build`): `Body` (torso and neck), `Head` (skull, snout, nose, eyes with a catchlight, pointed, round or broad ears, antlers), `Tail` (thin, a brush or a stub) and four `Leg`s. A species file only gives numbers: sizes at real scale, colours, jump height and how big a thing it carries. Parts are smooth solids along a curve with elliptical sections (`solid()`) and blobs (`blob()`) in `parts.ts`, with no seam, so normals are smooth.
3. **Legs are placed, not swung.** `Leg.reach(target)` bends a two-segment leg to put its foot on a point (two-bone inverse kinematics): the middle joint points forward on a front leg (the wrist) and backward on a hind leg (the hock) and a bird's (the ankle). The animal puts each foot on the ground in the rig's space and converts it into the leg's space through the torso's matrix, so a torso that bobs, rocks and rolls still leaves planted feet where they are. The leg first swings out at its joint toward the target; solving only in its own plane ignored the roll, and planted feet slid sideways as the body swayed.
4. **Gaits** are worked out from the legs' length (`gaits()`). The walk is the four-beat walk of dogs and cats (left hind, left fore, right hind, right fore, a quarter stride apart; duty 0.65); the run a gallop (the hind feet close together, then the fore; duty 0.3), the body rocking. A gallop stride of 1.4 leg lengths put the planted foot out of reach at both ends, where it lifted and slid. It is 1 leg length, with less time down (so the speed comes from flying through the rest), and the body sinks into each gait. Check it numerically for every animal: the share of frames a foot is planted equals the duty, and a planted foot moves less than 0.1 mm a frame.
5. **One coat material, coloured per vertex**: white in the theme's finish, times colours mixed from the new `fur` role with `trim`, `light` and `dark`. The fox is fur far toward trim with light chest and tail tip and dark stockings; the wolf grey; the bear fur darkened; the deer tan with bone antlers; the bird a robin (a trim breast); the snake olive with dark saddles. `twoTone()` puts the belly colour underneath.
6. **The bird** has its own body (`Bird.ts`, `Wing.ts`) on two `Leg`s with claws. Its head jerks forward with each step and holds still between, like a pigeon's. Its jump is a hop with the wings spread and beating. A folded wing lies along the body, so turning it about the body's length only rolls it: it spreads by swinging out about the shoulder (`rotation.y`) and beats about the body's length (`rotation.z`), in rotation order ZYX. Running, it leans forward, which carried its hips ahead of the feet and out of reach, so each stride is centred under the leaned hip.
7. **The snake** (`Snake.ts`) is one tube along a spine, reshaped every frame (its bounds go stale, so it isn't frustum-culled). It slithers: its body lies along a wave fixed on the ground (`x = A sin(k (travel + z))`), so as it moves forward every part follows the same wave and nothing slides sideways, the snake's version of planted feet. Its head swings half as far over the front 15% of the body, which slides about a millimeter there; the rest doesn't. Standing still, it keeps its last curves.
8. **Held figures go in the mouth** (a beak): turned so the longest level side lies across the mouth, centred on it, and scaled down to fit the animal (`hold`: 6 cm for the bird, 45 cm for the bear). The head lifts a little to carry it.
9. **Speech bubbles scale with the animal**: its height over the penguin's 55 cm, from 0.5 to 4 times. The camera that frames a deer stands far back, and at the penguin's size its words were a few pixels high. The snake, long but low, sets its own.
10. **Previews** (`animal()` in `previews.ts`): a demo like the penguin's (a greeting, a jump, carrying a fish, half a lap walking and a lap running, stopping where it began) round a circle sized to each animal. The camera views three-quarters from the side it starts on, aimed a little right of the circle's middle, so the circle stays clear of the panel. The Hold menu offers the fish, the fishing rod and the MIDI keyboard.
11. **Seeing motion**: a headless screenshot shows only the first second or so of a demo. To look at a gait or a jump, fast-forward the demo for the screenshot (a temporary loop calling the preview's `update` before it is shown), then take it out.
12. **Cost.** An animal is 2.6–11 k triangles in a handful of meshes, and builds in 5–25 ms.

## Objects

The objects live together in `src/figures/objects/` (lowercase, as the user named it), one file per object next to its spec: `Cliff`, `Cloud` and `Fog`, shown in the preview as `cliff`, `cloud` and `fog`. Their specs are drafts written from the code; they name no behaviour.

1. **Sized in three directions**: `new Cliff({ theme, seed, width, height, depth })`, in meters, each object with its own default (`Cliff.SIZE`: 10 × 6 × 4 m; the cloud 8 × 4 × 5 m; the fog 8 × 1.5 × 5 m). Each is built at about that size, then `fit()` in `parts.ts` stretches its geometry to fill exactly the box asked for, centred on x and z from y = 0 up. The numeric check builds each at its default and at other sizes and seeds and compares the box: they match to the centimeter.
2. **The cliff** is layers of rock (strata) of different thicknesses, each standing out or back along the face, so ledges, overhangs and worn bedding grooves come and go. The face bows in bays, leans back about 7°, and is broken by joints and cracks. Its ends step down layer by layer, and fallen boulders lie at its foot. It is flat-shaded rock in `scene.stone` like the lake's stones, darker in cracks and under overhangs, each layer a shade apart so the strata show. About 9 k triangles.
3. **The cloud** is a heap of the trees' lumpy clumps in tiers, shrinking as they rise to a few towers, with small billows over its top and sides, and cut flat below. It is `light`, shaded greyer toward its underside. It is far smaller than a real cumulus so it fits the scenes, and it doesn't float by itself: the preview lifts it 3 m. About 47 k triangles.
4. **The fog** (an object in the scene, not the scene's own fog, which the lake's weather controls) is a few hundred soft oval puffs. Each faces the camera, turned on the graphics card, and together they make one instanced mesh. Its colour is `scene.background` lightened toward `light`. It is transparent, writes no depth, casts no shadow, and fades out just above the ground so it never ends in a hard line. The puffs are big and many, because the Kuwahara filter wipes out sparse small ones. It drifts and swirls slowly on its own (`update(delta)`, its idle motion like the lake's waves): a puff that drifts out of one side comes back in at the other, thinned to nothing at both, so it loops for ever. Low-lying and 1.5 m tall, it reads as a flat bank from the preview's camera.
5. **They start on the lawn** (`figureEnvironments`): they are 8–10 m across, and the floor is only a 20 m square.

## Stories

A story plays a scene: its figures in its own environment, moved by a script or by outside input. The panel's Story tab or `?story=<name>` plays one, and `none` goes back to the picked figure. While a story plays, the figure tree and the environments are greyed out with a note saying why, and keep their picks.

1. **A story lives in `src/story/<name>/`**, next to its spec `<name>.md`, which belongs to the user like a figure's spec. The folder and file names are snake_case, as the user named the first one (`piano_play`). Its code, `<name>.ts`, exports a `Story`: `{ environment, create(theme, environment) => Preview }`. Register it in the `stories` table in `src/stories.ts`; the Story tab lists them in table order.
2. **A story that listens to outside input stops in `dispose()`.** The stage calls a preview's `dispose()` when it replaces it, before freeing it. Without it, a story left behind would still act on messages.
3. **OSC (Open Sound Control) comes through the dev server.** Browsers can't receive UDP, so `osc-bridge.ts`, a Vite plugin, listens on UDP port 57121 (`OSC_PORT` to change it) on this machine only (127.0.0.1 and ::1). It also takes OSC over HTTP: `POST /__osc` with one packet as `application/octet-stream`, answered 204, or 400 with the reason. That route works from anywhere the dev server can be reached, through ngrok or a VS Code tunnel. It reads OSC 1.0 messages and bundles (a bundle's time tag is ignored: messages play as they arrive) and passes each message on to the page as the Vite event `osc:message`. In the page, `onOsc(listener)` in `src/osc.ts` listens and returns the function that stops. Only `npm run dev` has the bridge, not a built page. It logs once where messages come from, and warns about a packet it can't read.
4. **Vite starts a restarted server before it closes the old one**, when a config file changes. The bridge therefore opens its port once the new server is listening; opened at once, it found the port still taken (`EADDRINUSE`) and OSC stopped until a manual restart.
5. **`piano_play`**: the MIDI keyboard on `grass`, playing what OSC sends it. `/piano/chord "Am"` calls `PlayChord`, `/piano/note "E5"` or a MIDI number (`76`) calls `PlayNote`, and `/piano/release` lets go of every key. A chord or note stays down until the next one replaces it. A name the piano can't read is reported with `console.warn` and skipped. From Sonic Pi:

   ```ruby
   use_osc "localhost", 57121
   live_loop :piano do
     osc "/piano/chord", "Am"
     osc "/piano/note", 76
     sleep 1
   end
   ```

6. **Check a story with real OSC packets.** Start the test server with its own `OSC_PORT` (the user's dev server holds 57121) and send UDP packets from a small Node script, to 127.0.0.1 and to ::1. In the page, spy on what arrives by importing the same module (`import('/src/osc.ts')`) and calling `onOsc` from a DevTools `Runtime.evaluate`. Read the console warnings, and look at a screenshot for the pressed keys. After the story is switched off, a bad message must give no warning, which shows `dispose()` ran.
7. **Send OSC from the dev server's machine.** `npm run osc -- /piano/chord Am` sends one message, and `npm run osc:demo` plays a chord progression with a melody until Ctrl+C (`osc-send.ts`; `OSC_PORT` picks the port). UDP doesn't go through VS Code Remote Tunnels (a request for it was closed as not planned) or through ngrok, which both carry only TCP. So when the preview is reached through a tunnel, send from VS Code's terminal, which runs on the dev server's machine. For Sonic Pi on another computer, run `osc-relay.mjs` there (Node 18+, no packages; download it from the dev server at `/__osc/relay.mjs`): `node osc-relay.mjs <tunnel URL>`. It takes UDP on that computer's port 57121 and posts each packet to `/__osc`, one request at a time so nothing is reordered. Packets that arrive while a request is on its way go together as one OSC bundle. Sonic Pi then uses `use_osc "localhost", 57121`, as in `examples/sonicpi.rb`.
8. **Stop a test's child processes by PID.** On Windows, `child.kill()` on a process spawned with `shell: true` kills only the shell, and `npm run osc:demo` kept playing, holding the test's output open. Find it by its command line (`osc-send.ts --demo`) and stop that PID; never stop every `node.exe`. A Chocolatey-installed tool such as ngrok runs as two processes, the shim in `chocolatey\bin` and the real program in `chocolatey\lib`, so stop both.
9. **Playing by hand.** A preview whose figure can be played by clicking gives `press(part)`: it presses the part under the pointer and returns the function that lets it go, or null for a part that doesn't press. `piano_play` presses the key `MidiPiano.keyAt(part)` names. The stage listens for `pointerdown` in the capture phase, so it runs before the orbit controls' own listener. On a press it calls `stopImmediatePropagation()`, so holding a key and moving never turns the view, and it captures the pointer so the release arrives wherever the pointer lifts. Each pointer holds its own key, so two fingers play two keys. Anywhere else, dragging turns the view as before. To test, project a key's top face through the story's camera to find it on screen, press it with DevTools `Input.dispatchMouseEvent` or `dispatchTouchEvent`, and check a screenshot.

## Keyboards and pianos

1. **Tuts** means keys. A keyboard includes its sharps (black keys) unless the user explicitly asks for white keys only. One octave = 7 white + 5 black keys, and two octaves (C4–B5, MIDI 60–83) = 14 white + 10 black keys.
2. Build keys by looping over MIDI note numbers. A note is black when `note % 12` is 1, 3, 6, 8 or 10. A black key is centered on the boundary between the white keys on either side of it.
3. Real sizes: a white key is 23.5 mm × 150 mm, and a black key is 13.7 mm × 95 mm, sitting about 1 cm higher. The key pivot is the back of the key.
4. A cute/toy keyboard may use wider keys for a chunky look (the MIDI keyboard uses 30 mm white and 17.5 mm black keys). Scale black keys by the same ratio as the white keys, and note the choice in a comment next to the constant.

## Colour and theme

Colours matter because a brand will be brought in, so its colours must look the same on every figure and in every scene.

1. **No figure hardcodes a colour.** Every colour comes from a `Theme` in `src/theme.ts`. A figure takes `{ theme }` in its constructor (default `defaultTheme`) and builds its materials from it in a `createMaterials(theme)` function.
2. **Colours are named by role, not by object:**

   | Role | Used for |
   |---|---|
   | `body` | main surface, the brand's primary colour |
   | `trim` | secondary surface: feet, rims, panels |
   | `light` / `dark` | light and dark neutrals: white and black keys |
   | `ink` | small details drawn on `body` (printed marks, labels) |
   | `marker` | indicators on knobs and wheels |
   | `metal` | metal parts: plates, pedals |
   | `wood` | bare or varnished wood: planks, benches, a rudder (shaded by the wood-grain texture) |
   | `fur` | an animal's coat, which each animal mixes with `trim`, `light` and `dark` into its own (see [Animals](#animals)) |
   | `accent` | every control (knobs, pads, buttons) |

   A new figure maps its parts onto these roles. Add a new role only when no existing one fits, and then add it to every theme.
3. **The scene belongs to the theme too.** Background, floor, `water` (a lake's surface, see [Environments](#environments)), `stone` (lakeside rocks, which must stand out from the floor), `grass` (a lawn's blades; a real green only where the palette allows one: in `felt`, and not in the brand, whose green is for controls), `flower` (blossoms, such as chives' flower heads, which must stand out from `grass`: a lilac in `felt`, and in the brand slate 400 with 5% indigo, the most tint it allows), the hemisphere light (`sky`, and `ground` for the bounce off the floor) and the key light all come from `theme.scene`. A palette built from scratch may tint `ground` so that shadows pick up the brand colour. When a real brand defines its surfaces, follow those instead: getresolved keeps the scene neutral grey.
4. **Pairs that sit on top of each other must contrast:** `ink` on `body`, `marker` on `accent`, `dark` on `light`. A white marker on a yellow knob is hard to see, so the purple theme uses a dark violet (900) marker. The studio theme first had `ink` = `body` (both black), and details drawn in `ink` disappeared.
5. **A real brand's rules come first.** When a brand defines its colours, take them from its own source (guideline and design tokens), record them in a `brand_<name>.md` doc next to this one, and map them onto the roles there. Rules 6 and 7 below only apply when designing a palette from scratch. The current brand is getresolved.id: see [brand_getresolved.md](brand_getresolved.md).
6. **Build a palette from one hue in steps.** When designing from scratch, make a scale from 50 (palest) to 900 (darkest) and assign it: 50 background, 100 floor, 200 ground light, 400 body, 600 trim, 800 dark, 900 ink and marker. The `purple` theme is the example.
7. **Exactly one accent colour.** Only one hue may sit outside the brand hue. If the brand names an accent, use it (getresolved's green). Otherwise use the colour opposite the brand hue on the colour wheel (yellow for violet, mint for pink). Every control uses it, so all knobs have the same colour. Don't add extra colours for variety; three different knob colours (yellow, teal, pink) broke the palette. `metal` (gold with violet) may sit near the accent, and so may `wood` (honey with violet), since both are natural materials. A brand with no brown (getresolved) gets weathered grey wood from its neutral greys instead.
8. **Colour-accurate rendering: no tone mapping.** `applyRendererTheme` sets `outputColorSpace = SRGBColorSpace` and `toneMapping = NoToneMapping`. Hex values are sRGB, and a lit face shows its hex value times its shading. Neutral tone mapping was used first, but measuring showed it turns the brand indigo `#4F46E5` into `#3224CE`, because it darkens low colour channels and oversaturates colours like indigo. With no tone mapping, it renders `#4941D3`. Keep light intensities in the theme so that colours don't drift between scenes.
9. **Measure, don't eyeball.** After changing a theme, lights or rendering, screenshot the scene and sample the pixel colour of the main lit faces (for example with `System.Drawing.Bitmap.GetPixel` in PowerShell). Compare them with the brand hex, and record the measured values in the brand doc.
10. A lit surface is never exactly its hex value, because light and shade change it. When a brand swatch has to match exactly (a logo, a flat colour patch), use `MeshBasicMaterial`, which is unlit.
11. Themes available: `felt` (default), `getresolved`, `getresolved-dark`, `purple`, `pastel`, `studio`. Pick one in the Theme menu on the panel's Settings tab or with `?theme=<name>` in the URL.

## Cute style

The MIDI keyboard shows this style. When the user asks for "cute":

1. Round the edges, but only a little. The user found a 12 mm body radius and 5 mm key radius "too bubbly". The accepted amount is **6 mm on the body, 2.5 mm on white keys and 2 mm on black keys**, with a 1.5 mm gap between keys.
2. Use a soft palette: the `purple` theme or `pastel`.
3. Make it glossy like toy plastic: the theme `finish` is `roughness 0.45`, `clearcoat 1`, `clearcoatRoughness 0.15`.
4. Use low domed knobs (a cylinder with a flattened half sphere, scaled to 0.3 in height) and little round feet.
5. No face or other decoration unless asked (see [Building shapes](#building-shapes)). A face (eyes, cheeks, smile) was tried on the left panel and removed.
6. If a word in the request is unclear (for example "bumble": bubbly or bumblebee?), pick one reading, say which one you picked, and make the other one easy to switch to (such as a colour option).

## Checking the result

1. Type-check after every change: `npm run typecheck` in `typescripts/animation`. It checks the page (`tsconfig.json`) and the dev-server code (`tsconfig.node.json`: `vite.config.ts`, `osc-bridge.ts` and `stream-bridge.ts`).
2. Look at it, don't only compile it. Start a test server on a spare port and take a screenshot with headless Edge:

   ```powershell
   $p = Start-Process node -ArgumentList 'node_modules/vite/bin/vite.js','--port','8099','--strictPort','--host','127.0.0.1' -PassThru -WindowStyle Hidden
   & "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless --use-angle=swiftshader --enable-unsafe-swiftshader --virtual-time-budget=5000 --window-size=1000,700 --screenshot="shot.png" http://127.0.0.1:8099/
   Stop-Process -Id $p.Id -Force
   ```

   Wait until the server answers before taking the screenshot. Start Vite with `node`, because `npx` can't be started from `Start-Process`. Never use port 8087 for tests, since that is the user's dev server. Other sessions may be testing at the same time, so if 8099 is taken, use another spare port. Stop the test server by its PID.
3. To look at a small figure up close, change its preview's `camera` in `src/previews.ts` only for the screenshot, and restore the file afterwards.
4. Three.js r186: `PCFSoftShadowMap` is deprecated, so use `PCFShadowMap`. `THREE.Timer` is in the core, so use `timer.update(time)`, `getDelta()` and `getElapsed()`. While the page is still busy loading, the first frame's `time` can be earlier than the timer's start, which gives a negative delta. The stage clamps it at 0, because a negative elapsed time crashed the MIDI keyboard demo.
5. The preview fits the sun's shadow to the previewed figure (`Stage.fitShadow()` in `src/Stage.ts`, called whenever a figure is shown): the shadow camera covers the figure's footprint and the shadow a tall part throws (about 0.65 × its height), at least ±0.52 m, and the sun sits far enough out to be above the figure's top. Too-large bounds make small figures' shadows blurry. Too-small bounds, or a sun below a mast's top, cut shadows off.
6. The shadow's offsets grow with those bounds (`bias -0.0005`, `normalBias = 0.01 × reach`), because each shadow texel covers more of a big figure. Without them, large or thin surfaces (a sail, a hull) show stripes of shadow acne.
7. **Screenshots of a moment in motion**, such as a leap that lasts 1.4 s, need exact frames. Drive headless Edge through its remote-debugging protocol, and before the page loads (`Page.addScriptToEvaluateOnNewDocument`) wrap `requestAnimationFrame`, so that every frame hands the stage a clock that moves exactly 1/60 s and stops at a chosen frame. The stage then keeps drawing that frame (with a delta of 0) until the clock moves on. Find the frames in a numeric run of the same preview in Node. With software rendering the Kuwahara filter makes each frame take seconds, so play the frames with `?kuwahara=0` and turn the filter on only for the paused frame, through the page's own settings module: `import('/src/settings.ts').then((s) => s.setKuwahara({ on: true, radius: 5 }))`. Look at a larger window too (1600×1000): a detail that vanishes at 1000×700 may read at a typical size.
8. **Numeric checks run the real modules in Node** through Vite's `createServer({ root, configFile: false, appType: 'custom', server: { middlewareMode: true } }).ssrLoadModule(...)`; `vite-node` is not installed. `configFile: false` keeps the OSC bridge from starting, and a test server started from `vite.config.ts` needs its own `OSC_PORT`, since the user's dev server holds 57121.
