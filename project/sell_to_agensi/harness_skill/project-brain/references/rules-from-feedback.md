# Rules from feedback

An agent forgets everything between sessions except what is written down. Every time the user corrects it, the correction is worth writing down once, so no later session needs it again. This file is how.

## What to record

Record:
- **Corrections:** "don't do X", "stop doing Y", "that's wrong, do it like this".
- **Confirmed approaches** that weren't obvious: the user picked one of several ways, or said "yes, exactly like that" about an unusual choice.
- **Decisions with lasting effect:** a stack, a naming scheme, a folder layout, a market, a tone of voice.
- **Standing approvals and refusals:** "you can always run the tests without asking", "never publish anything without asking me".

Don't record:
- One-off instructions that only apply to this task.
- What the code, config, git history or README already say. Point to it instead.
- Your own guesses about what the user might want.

## Where

| Scope | Place |
|---|---|
| This project | the project's agent file (`CLAUDE.md` / `AGENTS.md`), in the section the rule is about (Commands, Knowledge, Tasks, Ask first...) |
| Every project of this user | the user-level agent file (Claude Code: `~/.claude/CLAUDE.md`) |
| One area of a big project | the agent file in that folder, or a doc it links to |

Unsure whether a rule is project-wide or personal: ask, in one line.

## Format

```markdown
**<The rule as an instruction>** (the user, <YYYY-MM-DD>: "<their words>"). <Reason, if not obvious.> <How to apply it, if there are edge cases.>
```

- The quote preserves intent. "Don't sync aggressively" is not the same rule as "never sync"; a paraphrase loses that.
- The date orders rules: when two conflict, the newer one wins.
- The reason lets a later session handle a case the rule doesn't name.

## Good and bad

| Bad | Why | Good |
|---|---|---|
| The user got annoyed that I synced too often. | A story, not an instruction. | **Ask before writing summaries** (the user, 2026-09-25: "don't summarize aggressively, ask me first"). Finish the edits, then ask once: which files changed and how many summaries are pending. |
| Use pnpm. | No reason: a later session can't judge an edge case. | **Use pnpm, not npm** (the user, 2026-10-02). The lockfile is `pnpm-lock.yaml`, and CI fails when a `package-lock.json` appears. |
| Be careful with the database. | Not actionable. | **Never run migrations against `prod`** (the user, 2026-08-14: "prod migrations only through the deploy pipeline"). Locally use `make migrate-dev`. |
| Don't add extra features. Don't add titles. Don't add overlays. | Three rules for one idea. | **Build only what was asked** (the user, 2026-10-12: "no text overlays I didn't ask for"). Suggest extras in one line instead of adding them. |

## Keeping rules healthy

- **One rule, one place.** Before adding, search the agent file. Update the existing rule instead of writing a second one that half-overlaps.
- **Widened or narrowed:** edit the rule and add the new date: `(the user, 2026-09-24, widened 2026-10-18)`.
- **Wrong or obsolete:** delete it. A rule now enforced by a linter, test or hook can shrink to a pointer to that check.
- **Too long to be a rule:** move the explanation into a doc in the knowledge graph, and leave a one-line rule linking to it.
- **Tell the user** what you recorded: "Added to CLAUDE.md > Tasks: commit only when the task says so."

## The user's spec files

Some files are the user's specification for what the project should be, written by the user and for the agent to implement. Mark them at the top, for example:

```markdown
# Knowledge tool
**AI: do not edit this file.**
```

For such a file:
- Never edit it, even to fix a typo. Point the typo out instead.
- Implement what it says. Where it is vague, decide, record the decision as a rule in the agent file (with the date), and tell the user.
- When it changes, re-read it, list what the work no longer matches, and bring the work in line.
- Where the agent file records decisions that go beyond the spec, say so in the rule ("goes beyond the spec's X, at the user's request, <date>").

This is how a short spec grows into a large, consistent piece of work: the spec stays the user's, and every decision taken while implementing it ends up as a dated rule.
